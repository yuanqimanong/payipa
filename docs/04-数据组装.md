### 1.2 研判（2026-07-04；**第 2 轮需求方「基本可以」全部确认**，动态加字段补充图解见 §2.1）

1. **组装产物查看：强烈建议复用 03 那套**。产物表就是标准混合 schema（系统列+JSONB），03 的 Tabulator remote 查询后端、筛选排序、详情竖排、导出全部原样可用；只是**入口不同**（组装产物列表页）+ **外挂不同**（数据集描述、对外 API 发布开关）。全新做一套 = 双份维护零收益。
2. **Query Gateway：方向认可**——比裸 SQL 面窄（结构化 API 无注入面）、比「主控预取推送」灵活（脚本可按需迭代拉取）。设计要点：
   - API 形态：**结构化 table API**（表/列/过滤/keyset 游标，不收 SQL 字符串），返回 **Arrow IPC 流**（pandas/polars 零拷贝读入）；
   - **job_token = JWT**（PyJWT 已在栈内）：主控按次签发，scope = 本次组装可读的表清单 + 行数配额 + 有效期（=任务租约时长），aud = job_id，用完即废；
   - 沙箱网络出口**只允许到 gateway**（egress 白名单），DB 凭证零接触；
   - **写路径建议对称 agent 模式**：产物**不经 gateway 直写库**——沙箱产 parquet → presigned 直传对象存储 → 回传指针 → **主控校验后装载入业务库新表**。密钥不出主控、入库动作集中主控（与 01 agent 模式同构，排查一致）。
   - 归属划分：gateway 服务端 = apps/server 内一组端点（v1 同进程）；API 形状进 contracts；**jbutils 放泛用零件**（Arrow 流读取助手、s3 分片已有），沙箱内固定方法（`read_table(...)` 等）是 payipa 侧薄胶水——jbutils 不装 payipa 业务语义。
3. **数据读取封装（对口述-2 的问号）**：即上条 gateway 的沙箱侧 SDK；泛用件靠 jbutils、业务胶水在 payipa。
4. **产物 = 业务库新表：赞成**，沿用 02 混合 schema——产物表也带数据指纹唯一索引、created_at/updated_at、state，天然接 03 查看与 05 推送。
5. **全量 vs 增量：对，按业务配置**（组装任务配置项）。增量正确性**两件套**：
   - **读侧水位**：每次运行记录消费到的源表位置（max(id) 或 updated_at 水位），下次从水位起拉——保证「只处理新数据」；
   - **写侧指纹幂等**：产物表自身的数据指纹唯一索引 + `ON CONFLICT` upsert——重复处理也不产生重复行（你说的「数据指纹 id」正是写侧答案）。
   - 两者合用 = at-least-once 读 + 幂等写 ≈ 恰好一次效果。
6. **可重算性**（解释 + 方案）：指**同一输入重跑能得到同一产物**——排错、回填、修复的基础。三要素（全部由已有机制组合，零新造）：①脚本版本 pin（内容寻址 hash，01 机制）；②**输入范围记录**（每次运行日志记消费的水位区间/批次清单）；③写侧幂等（上条）→ 重跑不重复。版本控制本身复用 01/02 那套（状态机+还原+test 通道试跑不入正式表）。
7. **资源限额三层**（推荐）：
   - **进程级**：沙箱容器 cgroup——内存上限（超限 OOM kill）+ CPU 配额；
   - **任务级**：执行超时（主控租约，07 机制复用 + 沙箱内硬超时）、**读入行数配额（内嵌在 gateway 的 job_token 里）**、产物大小上限（parquet 落地检查）；
   - **并发级**：沙箱 worker 池大小（07 槽位思想复用）。

## 2. 技术调研

> 核验 2026-07-04。

### 2.1 产物表结构动态演进（回答口述-4「5 字段改 10 字段」）

- **本项目答案基本免费**：产物表沿用 02 混合 schema——新字段落 JSONB = **零 DDL**；需索引的字段 `ADD COLUMN`（PG 11+ 元数据级瞬间完成，本会话已核验）。
- **业界同款策略 = 加法式演进（additive schema evolution）**：Delta Lake `mergeSchema` / dbt `on_schema_change` 的共同原则——**源里新增的列自动加到目标表，但不删列、不改已有列类型**；破坏性变更（删列/改类型）不自动执行（learn.microsoft.com、databricks.com）。
- 落地流程：每次组装运行，从脚本输出 DataFrame 推断 schema → 与现表 diff → **加法自动应用**（JSONB 键新增无操作；新提升列 ADD COLUMN）→ **破坏性变更拦截**：默认拒绝并提示（人工确认或建新版本表）。
- **补充图解（第 2 轮，回应"没理解"）**：用户字段不是表的真列——整包存在一个 `fields` JSONB 列里。5 字段改 10 字段时，新行的 JSON 里多 5 个键、老行保持 5 个键，**表结构零变化**（PG 眼里始终是那 6 列），系统只登记字段元数据供界面展示——是记账不是改表。真正碰表结构只有两种情况：①字段勾「需索引」→ 一次 `ADD COLUMN ... GENERATED ALWAYS AS (fields->>'x') STORED` + 建索引（PG11+ 元数据级瞬间）；②改类型（删字段都不用动作）→ 拦截找人（重算或新版本表）。

### 2.2 沙箱隔离技术初探（详见 [04A](04A-沙箱执行服务.md)）

- 业界共识：**Python 无法在语言层内沙箱**（解释器高度可内省，对象图/frame 可逃逸）——必须 OS 级隔离。候选梯度：nsjail（namespace+seccomp+cgroup，最轻，Windmill 生产在用）< 容器+gVisor（用户态内核，I/O 开销 10–30%）< Firecracker microVM（独立内核最强，~125ms 启动）。（github.com/restyler/awesome-sandbox、northflank.com 等）
- 本项目语境：执行的是**管理员签名后的脚本**（02 已定），威胁模型弱于公开 SaaS；沙箱又是可选部署。**倾向：v1 = 容器 + cgroup（+nsjail/gVisor 加固可选）**，Firecracker 属过度——威胁等级在 04A 与需求方对齐。

## 4. 定案（2026-07-04，详见 [决策记录.md](决策记录.md)）

1. **触发**：数据任务批次完毕自动触发组装；数据任务配「关联组装任务 id」；触发/完成日志可见。
2. **脚本环境**：预装 pandas + Polars；固定方法名约定与 02 统一设计（遗留）。
3. **产物 = 业务库新表（落 `business` 库，[09 §1.3-3](09-部署运维.md)）**（沿用 02 混合 schema：指纹唯一索引/created_at/updated_at/state/JSONB）；**表结构加法式演进**（JSONB 零 DDL + 勾索引 ADD COLUMN + 破坏性变更拦截）。
4. **产物查看复用 03 查询组件**（入口=组装产物列表页；外挂=数据集描述+对外 API 发布开关）。
5. **数据供给 = 自研 Query Gateway**：结构化 table API（不收 SQL）+ job_token JWT（scope=可读表+行数配额+租约时长）+ Arrow IPC 流；沙箱出口仅放行 gateway、零 DB 凭证；**写路径对称 agent 模式**（parquet→presigned 直传→回指针→主控装载入库）。
6. **全量/增量按业务配置**；增量正确性 = 读侧水位 + 写侧指纹幂等 upsert。
7. **版本控制复用 01/02 机制**；可重算三件套 = 脚本版本 pin + 输入范围记录 + 写侧幂等。
8. **资源限额三层** = 容器 cgroup（内存/CPU）+ 任务级（租约超时/token 行数配额/产物大小）+ worker 池并发。
