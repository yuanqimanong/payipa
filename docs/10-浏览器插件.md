# 10 · 浏览器插件（网页点选取数）

状态：**已定案**（2026-07-03 开启，2026-07-04/05 收口；正式分发方式产品化阶段定）

## 1. 需求对齐

需求方口述要点（2026-07-03，第 2 轮）：

- 用户在配置网站规则时，新增字段有两种填法：
  1. **手填 XPath**；
  2. **启动浏览器插件**，在目标网页上**点选元素**，对应的 **XPath/CSS 自动回填**到 pyp 配置界面。
- 部署形态约束：**pyp 服务部署在服务器上，用户在自己的机器上**使用浏览器 + 插件。
- 问题：插件与平台如何连通？插件代码是否也放在 pyp 目录（仓库）下、作为单独一部分？

待需求方拍板的问题清单：

1. 插件 ↔ 平台的连通架构（直连服务器 API / 浏览器内与平台页面直通 / 其他）？
2. 插件代码归属（monorepo 内 `extensions/` 目录 / 独立仓）？
3. 目标浏览器范围（Chrome / Edge / Firefox）与分发方式（商店上架 / 自分发）？

## 2. 技术调研

> 事实核验于 **2026-07-04**（官方文档 + 一手来源）。

### 2.1 平台事实（Manifest V3 / 浏览器现状）

- **MV2 已彻底死亡，只做 MV3**：Chrome 自 2024-10 起在稳定版逐步禁用 MV2，Chrome 139（2025 年中）连企业策略 `ExtensionManifestV2Availability` 豁免也移除，全量强制 MV3（来源：developer.chrome.com MV2 deprecation timeline）。
- **MV3 service worker 生命周期**：空闲 **30 秒**被杀，收到事件/调用扩展 API 会重置计时；单个请求处理超 5 分钟、fetch 响应超 30 秒也会被终止。保活手段：Chrome 116+ **活跃 WebSocket 消息可重置空闲计时**（可用心跳保活）、chrome.alarms（120+ 最小间隔 30s）、Offscreen API（109+）。设计原则：不要假设后台常驻，状态落 storage，事件驱动。
- **externally_connectable（网页直接向扩展 sendMessage）**：Chrome/Edge 支持，manifest 里声明允许的网站域名白名单即可让平台页面直接与扩展通信；**Firefox 至今不支持**（bugzilla 1319168，2016 年开issue，2025-11 仍未实现）——跨浏览器方案必须准备 content script + `window.postMessage` 中转这条后备通路。
- chrome.sidePanel API 已稳定多年（Chrome 114+；基于既有知识，本轮未单独核验）；Firefox 对应的是 sidebar_action，API 不同。

### 2.2 同类产品的连通方式

- **Web Scraper.io**（与本需求最同构）：浏览器扩展做**点选式规则编辑器**（sitemap = 起始 URL + CSS/XPath 选择器集），本地即可跑；Web Scraper Cloud 用**扩展里构建的 sitemap** 跑云端任务——扩展是「编辑器」、云端是「执行器」，账号登录同步。这与我们「插件点选 → 平台配置」的分工一致。
- Simplescraper / Browse AI 等同类均为「扩展录制/点选 + 云端执行」形态（连通细节未逐家核验）。

### 2.4 可行架构对比

| 维度 | A. 插件直连服务器 API | B. 同浏览器内直通（推荐起点） | C. sidePanel 内嵌配置面板 |
|---|---|---|---|
| 数据路径 | 插件 → HTTPS API → 服务器 → SSE/WS → 平台 UI 页 | 平台 UI 页 ↔ 扩展（externally_connectable；Firefox 走 content script+postMessage 中转）↔ 目标页点选 | 点选结果直接填入扩展侧边栏内的配置面板 → 面板调服务器 API 保存 |
| 配对/登录 | 需要（插件里登录或粘贴配对 token） | **不需要**——manifest 白名单限定平台域名即是信任边界，UI 页自身已有登录态 | 需要（面板内登录） |
| 时延 | 一次服务器往返 | 浏览器内，毫秒级 | 浏览器内 |
| 服务器侧工作量 | 新增回填 API + SSE 通道 + token 管理 | **零**（复用 UI 已有保存接口） | 无新增，但配置 UI 要在扩展里重做一份 |
| 安全面 | 多一组对外 API 与 token 生命周期 | 小；注意 postMessage 校验 origin | 中；扩展内持登录态 |
| 跨浏览器 | 好（纯 HTTP） | Chrome/Edge 原生；Firefox 需后备通路 | Chrome/Edge 好；Firefox sidebar API 不同 |
| 适用 | 插件独立使用、UI 未打开的场景 | UI 与插件同浏览器（正常使用形态） | 想要「目标页旁边就是配置面板」的重交互 |

**推荐**：以 **B 为起点**——用户本来就是在浏览器里开着平台配置页操作的：配置页点「点选」按钮 → 经 externally_connectable 通知扩展 → 扩展在目标页 tab 注入点选器（高亮元素、点击生成 CSS/XPath）→ 结果经扩展回传配置页自动填充 → 配置页用自己已有的登录态保存。全程不新增服务器面，无配对流程。Firefox 支持后备通路留作后期。C 可作为 v2 交互增强，A 在「插件脱离 UI 独立采集」需求出现时再加。

### 2.5 发布渠道与审核红线

- **Chrome Web Store 远程代码禁令**（MV3 政策）：所有逻辑必须打包在扩展内；`eval()` 远程字符串、甚至「内置解释器执行远程拉取的复杂命令（哪怕以数据形式拉取）」都算违规；**拉取远程配置/数据/图片是允许的**。对本插件的含义：点选器逻辑全部内置，与平台交互只传「数据」（选择器结果、简单配置），**不要设计成平台向插件下发可执行规则/脚本**。
- 分发：Chrome 普通用户实际只能走商店（自加载 unpacked 仅开发者模式；企业策略分发另说）；Edge Add-ons 独立商店（MV3 兼容）；Firefox 需 AMO 签名（可自分发已签名 xpi）。
- 目标浏览器建议：v1 只做 **Chromium 系（Chrome/Edge 同一份代码）**，Firefox 后备通路等有真实需求再上。

## 4. 定案

（2026-07-04 拍板，详见 [决策记录.md](决策记录.md)；本节 2026-07-04 补同步）

1. **连通架构 = B「平台 UI 页 ↔ 扩展浏览器内直通」**；Chromium 主路径采 **content script + `window.postMessage` 桥**（替代 externally_connectable，一举免去扩展 ID 发现与部署域名白名单，信任边界靠 origin 校验）；零服务器新增面、无配对流程。
2. **代码归属 = monorepo `extensions/picker`**；逻辑全部打包（商店远程代码禁令），平台 ↔ 插件只传数据。选择器库按 htmx/tabulator 方式 **vendored 单文件静态引入、不引 node 构建链**；`extensions/picker`（非 Python 包）**排除出 uv workspace members 与 import-linter**。（M5）
3. **浏览器范围 = v1 仅 Chromium 系（Chrome/Edge 一份代码）**；content script + postMessage 桥本即跨浏览器通路，Firefox 复用同一份桥、留待真实需求。

4. **开发阶段不上架商店**（2026-07-05 拍板）：unpacked 开发者模式自加载调试（Chrome/Edge「加载已解压的扩展程序」）；是否上架等产品化阶段再定。
