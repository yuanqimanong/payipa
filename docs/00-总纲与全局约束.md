### 2.1 Python 3.14 风险评估

**结论：低风险，可作为新项目默认版本（普通 GIL 构建）。**

版本现状：

- 3.14 最新 patch 为 **3.14.6**（2026-06-10），GA（2025-10-07）至今 9 个月、6 个 patch，早期回归窗口已过；常规 bugfix 支持到 **2027-10**，security 到 2030-10（PEP 745）。
- 对照 3.13：最新 3.13.14，但按惯例其常规 bugfix 约 **2026-10 收尾**（推断，未逐条核验 PEP 719），此后 security-only——现在选 3.13 意味着几个月后就失去常规修复。
- 3.15 已 feature freeze（2026-05-07），final 计划 2026-10-01（PEP 790）。

依赖就绪度（21 个候选关键依赖逐一核验，**无一硬性阻塞**）：

| 状态 | 包 |
|---|---|
| 完全就绪（有 cp314 wheel 含 win_amd64，或纯 Python 且已声明支持） | FastAPI 0.139、Pydantic 2.13（2.12 起官方支持 3.14）、pydantic-core、SQLAlchemy 2.0.51（wheel 自 2.0.45 起，classifier 滞后）、asyncpg 0.31、psycopg 3.3、pandas 3.0.3、numpy 2.5、pyarrow 24、duckdb 1.5.4、polars（abi3 wheel）、greenlet 3.5、uvicorn、structlog、niquests、PydanticAI、Procrastinate 3.7+、pyrate-limiter |
| 需注意 | **Playwright**：1.61.0（2026-06-29）才加入 3.14 classifier，官方背书仅约 1 周——若采集依赖 Playwright，须先做 Win/Linux 双平台冒烟；**httpx**：停在 0.28.1（2024-12），2026-02 起维护者关闭全部 issues，Pydantic 已 fork 为 httpx2——新项目建议直接选 niquests 或跟进 httpx2 |

破坏性变化的实际影响：

- **PEP 649/749 注解延迟求值**：Pydantic 2.12 / FastAPI 0.128.1 / SQLAlchemy 2.0.45+ 均已消化，用当前版本无已知问题；残余风险只在「维护不活跃且运行时反射 `__annotations__`」的长尾库。注意 **Pydantic V1 在 3.14+ 不可用**，依赖树里不能有 `pydantic<2` / `pydantic.v1` 的库。
- **multiprocessing 默认 start method（对本项目最实质）**：Linux 默认由 fork 改为 **forkserver**（Windows 仍 spawn）。并行清洗/处理代码应按 spawn 语义编写（不依赖 fork 继承全局状态）——顺带抹平 Windows 开发 / Linux 生产差异。
- **free-threaded（无 GIL）构建**：3.14 起官方支持，但 psycopg-binary / duckdb / polars 无 cp314t wheel，greenlet FT 有罕见崩溃 caveat——**生产禁用**，普通 GIL 构建行为与 3.13 一致。
- 收益项：stdlib zstd（PEP 784，数据压缩直接受益）、子解释器、asyncio 内省工具、更长的支持窗口。

本地实测：uv 在 Windows 11 上可直接拉起 `cpython-3.14.6-windows-x86_64`，并以 `--only-binary` 面向 linux 平台完整解析数据栈（pandas 3.0.3）——双平台工具链就绪。

### 2.2 payipa + jianbing_utils 双项目并行开发（uv 机制）

uv 现状：最新 **0.11.26**（2026-06-30）；workspace / path / git sources / `uv build` / `uv publish` / `uv_build` 后端均为正式功能。注意 uv 仍处 0.x，官方允许 minor 版本破坏性变更，**CI 与 `[build-system].requires` 都要锁上界**（如 `>=0.11,<0.12`）。

「未发布时引入」共三种机制（均已对官方文档核验）：

**机制一 · 同仓 workspace**（若两项目放同一仓库）：根 `pyproject.toml` 写 `[tool.uv.workspace] members`，依赖用 `{ workspace = true }`；全仓单一 `uv.lock`，**workspace 成员永远以 editable 安装**（改 utils 即时生效）。限制：全体成员强制统一 `requires-python`（取交集）、共享一个解析结果；utils 想面向 PyPI 支持更宽 Python 范围时会被牵制。

**机制二 · 双仓 + path 依赖（本地兄弟目录）**——与「jianbing_utils 单独起项目」的意图吻合：

```toml
# payipa/pyproject.toml
[project]
dependencies = ["jianbing-utils>=0.1"]   # 标准版本约束，始终保留

[tool.uv.sources]
jianbing-utils = { path = "../jianbing_utils", editable = true }
```

- **`editable = true` 必须显式写**：path 依赖默认装「构建快照」，忘写则 utils 改代码不生效且报象隐蔽（高频坑）。
- 相对路径会以相对形式写入 `uv.lock`（可提交、跨机器可移植）；editable 在 Windows 经 `.pth` 实现，无需 symlink 权限。
- **lock 只锁「指向哪里」不锁「目录内容」**：跨仓 path 方案不保证可重现构建，CI/部署侧须改用 git tag/rev 或已发布版本；CI 若要用 path，需双 checkout 固定相对路径。

**机制三 · git 依赖**（CI/部署期推荐，直至发 PyPI）：`{ git = "…", tag = "v0.1.0" }`（或 branch/rev），lock 锁定到具体 commit；私有仓认证走 git credential helper（官方推荐），uv 不会把凭证写进 pyproject/lock。

发布与切换路径：

- jianbing_utils 构建后端选 **`uv_build`**（`uv init` 默认；纯 Python 库首选，零配置、默认 src layout；需要构建脚本时再换 hatchling）。
- 流程：`uv version --bump` → **`uv build --no-sources`**（官方建议：验证禁用 sources 后仍可构建，确保 `[project.dependencies]` 全部可从 registry 解析）→ `uv publish`（PyPI 用 Trusted Publishing；私有 index 用 `[[tool.uv.index]]` + `publish-url`）。
- **发布后切回 PyPI 只改一处**：删除 payipa `[tool.uv.sources]` 中的条目 + `uv lock`；`[project.dependencies]` 的版本约束原样即 PyPI 约束。需要联调未发布改动时临时加回 path source，diff 极小。
- 关键语义：`tool.uv.sources` 是 **uv 私有、仅开发期生效**的机制，打包产物不携带；「传递依赖的 sources 是否被尊重」上游未决（astral-sh/uv#9446）——私有源应集中声明在消费方，jianbing_utils 自身依赖必须全部来自公开 index。

**自动发布链路（jb 更新 → 自动发 PyPI → payipa 升版，2026-07-04 核验）**：

- **发布通道选 `uv publish` 原生 Trusted Publishing（OIDC）**：自 uv 0.4.16 支持，免 token；PyPI 侧配 pending publisher（新包首发自动转正，注意首发前项目名可能被抢注，应尽早占名）。Astral 有官方端到端示例（push tag `v*` → `id-token: write` + `environment: pypi` → `uv build` → 冒烟 → `uv publish`）。无需 pypa/gh-action-pypi-publish。
- **版本 / 触发（小工具库推荐最简）**：手动 `uv version --bump patch`（0.7.7 起默认同步 uv.lock）→ `git tag vX.Y.Z` → push 触发上面的 workflow。要全自动 changelog 再上 python-semantic-release（对 uv 有官方集成指南，注意 build_command 要 `uv lock --upgrade-package` 防 lock 失步）；release-please 因 uv.lock 无原生支持暂居其后。
- **测试矩阵**：`astral-sh/setup-uv` **v8 起无 `@v8` 浮动 tag，必须钉完整版本或 commit SHA**；矩阵 `python-version: ["3.11","3.12","3.13","3.14"]` + `uv sync --locked`，解释器由 uv 自带 managed CPython 提供。
- **下游 payipa 升级**：单内部依赖场景，发版后手动 `uv lock --upgrade-package jianbing-utils` 一条命令即够；依赖多则上 Renovate（对 uv.lock 支持最成熟）或 Dependabot（`package-ecosystem: "uv"`）。
- **⚠️ path 源与自动升级互斥（重要坑）**：若 payipa 把 `[tool.uv.sources]` 的 path 源**提交进仓库**，uv.lock 会把 jb 锁成本地路径来源，机器人/手动升 PyPI 版本全部失效，且 CI 无该路径直接失败。**约定：path 源只存在于本机开发态、不提交**（联调用 `uv add --editable` 临时加、还原再提交），或 CI 全链路 `--no-sources` 并接受重锁。这是双仓方案落地时必须遵守的纪律。

**双仓日常联调操作流程（2026-07-05 应需求方要求整理成清单；机制即上文已定决策）**：

1. **一次性设置（每台开发机）**：payipa 目录下 `uv add --editable ../jianbing_utils`——之后 **jb 源码改动即时生效**（editable 装的就是磁盘上的工作区代码），联调期**不存在版本问题**：跑的永远是两边的最新源码，无需发版、无需重装。
2. **提交 payipa 改动前**：还原 pyproject.toml/uv.lock 里的 path 源（本机态不进仓库）——这是唯一要记的纪律。
3. **jb 发版时**（功能稳定需要固化）：jb 仓 `uv version --bump patch` → commit → `git tag vX.Y.Z` → push → CI 自动 `uv build` + Trusted Publishing 发 PyPI（免 token）。
4. **payipa 跟进**：`uv lock --upgrade-package jianbing-utils` 一条命令锁到新版，提交 uv.lock——CI/部署从此用这个锁定版本。
5. **CI 需要未发布的 jb 改动时**：临时用 git 依赖（`{ git = "…", rev = "…" }`）而非 path。
6. **jb 侧红线**：依赖全部来自公开 index；发版前 `uv build --no-sources` 验证可脱离本机构建。

### 2.3 目录划分与微服务注意事项

外部主流做法（2025-2026 社区共识，与本场景吻合）：

- **按领域分包，不按技术层分包**（zhanymkanov/fastapi-best-practices ~17.6k stars；Kraken Technologies 2.7 万模块大单体实践）。FastAPI 官方「Bigger Applications」的按文件类型布局只适合小项目。
- **模块化单体起步、模块边界=未来服务边界**；先拆真正需要独立部署/隔离的进程，其余保持逻辑模块（与 Building Microservices「过早拆分=分布式泥球」一致）。
- **uv workspace 是 Python monorepo 的事实标准**：`members = ["apps/*", "packages/*"]`，apps 放薄入口、packages 放领域包；CI 可 `uv sync/run --package X` 按成员操作（Airflow 百万行级单仓同款路线）。
- workspace 成员内采用 **src layout**（packaging.python.org 官方推荐，防误 import 开发副本）；tests 每成员自带、顶层只留跨包集成测试。
- **模块边界必须用工具强制**，纪律条款不够：import-linter v2.13（Production/Stable，layers/forbidden/independence 三类契约，Kraken 每 PR 强制）或 tach v0.35（Rust 实现、支持公开接口白名单；已迁组织 tach-org，治理连续性有轻微不确定）。

针对本场景（爬虫任务管理调度 / 数据筛选查看 / 用户组装逻辑展示 / 推送与 API）做微服务要注意的清单：

1. **先问「为什么要独立部署」再拆**：值得第一天物理分进程的通常只有——API 入口（不能被长任务拖死）、执行长任务的 worker（独立扩缩重启）、运行用户代码的执行器（不可信代码必须物理隔离）。其余先做逻辑模块。
2. **契约先行**：模块间接口用 Pydantic schema 显式定义并版本化，放共享包；跨模块只经公开接口，禁止 import 对方内部实现（CI 用 import-linter/tach 强制）。
3. **数据边界**：谁拥有哪些表要明确；避免多服务随意写同一张表。拆分后跨服务一致性靠 outbox/幂等，不靠分布式事务。
4. **一切调用假设会失败**：超时、重试、幂等键从第一天设计进接口，否则拆开即雪崩。
5. **可观测先于拆分**：结构化日志 + trace id 贯穿，拆开后才能排障。
6. **部署复杂度是真实成本**：每多一个常驻进程就多一份配置、日志、升级与监控面——这也是「单体起步」的核心理由。

## 3.5 项目结构（v0.2，2026-07-04 整理）

> 依据已定决策整理：monorepo + uv workspace、pyp-agent 为 workspace 成员、浏览器插件在 `extensions/`、jianbing_utils 独立仓。标注「待定」的部分随模块讨论演进。

**术语对照——文档里的叫法对应哪块代码（2026-07-04 补，全部文档通用）**：

| 文档叫法 | 代码位置 | 是什么 |
|---|---|---|
| **主控端 / 主控 / 主节点** | `apps/server` **+** `packages/payipa-core` | 平台服务器侧的总称。**apps/server 是唯一常驻运行的进程**（薄入口：FastAPI 装配、应用 API、agent WS 接入端点、启动调度循环、监控 API、OpenAPI 文档）；**真正的业务逻辑全在 payipa-core 包里**（调度分发、分流入库、限流调频、规则库、存储抽象），server 只是把 core 装配起来跑。「任务下发给 agent」= server 的 WS 端点发出，内容由 core.crawl 的调度逻辑决定 |
| **子节点 / agent** | `packages/pyp-agent` | 部署到其他机器的采集执行端：出站 WS 连主控、抓取、大对象直传、回传结果与指针；只依赖 contracts，不依赖 core |
| **契约 / contracts** | `packages/payipa-contracts` | **纯定义包**：Pydantic 模型、枚举、协议版本号——只有「数据长什么样」，零业务逻辑、零 I/O、不运行任何东西；主控与 agent 唯一的共同依赖 |
| 前端 | apps/server 内 `templates/` + `static/` | 应用层 UI = **服务端渲染**（Jinja2 + HTMX，06 定案）；无独立 `frontend/` 目录、无 SPA/node 构建链 |
| 浏览器插件 | `extensions/picker` | 网页点选取数工具，与前端页面浏览器内直通（见 10 模块） |

## 3.6 payipa-contracts 契约包详解（2026-07-04 定）

**一句话职责**：`payipa-contracts` 是「协议定义层」——用 Pydantic v2 声明所有**跨进程/跨模块传递的数据形状**，不含任何业务逻辑、不碰数据库、不发网络请求。它是 agent 与主控之间、以及 core 内部模块之间**唯一被共同依赖的包**。

**为什么要独立成包（而非放在 payipa-core 里）**：

1. **让 agent 保持极小依赖**。pyp-agent 要通过 pip/docker 部署到很多节点机，安装包越小、依赖越少越好。若 agent 依赖 payipa-core，就会连带拖进 SQLAlchemy、存储后端、整个业务栈——完全没必要。agent 只需要「消息长什么样」，也就是 contracts。
2. **主控业务改动不牵连 agent 发版**。core 里改了某个业务实现、加了张表，只要契约没变，agent 就不用重新发布。契约成为一道**受控的、显式版本化的**变更边界——改契约是「破坏兼容」的信号，会被人注意到。
3. **契约可被第三方消费**。将来若要给 Dataset API 出 Python SDK、或让别的系统对接，直接依赖 contracts 即可拿到类型定义，不泄露内部实现。

**内容清单（模块级）**：

| 文件 | 定义什么 | 谁用 |
|---|---|---|
| `agent.py` | agent↔主控 **WebSocket 帧**：注册请求/应答、心跳、任务下发、状态回报、取消指令、错误帧 | agent + 主控 WS 端点 |
| `task.py` | **任务定义**：task_id、source、参数、**规则指针 `(rule_id, version, content_hash)`**、通道 `channel=test\|prod`、资源/限流提示 | agent + core.crawl |
| `rule.py` | **规则包 schema**（选择器/映射/清洗声明）、**版本状态机枚举** `draft→testing→active`、规则包 manifest（hash、依赖） | agent + core.crawl |
| `artifact.py` | **工件元数据**：`bucket / object_key / storage_backend / size / sha256 / etag / content_type / status`——注意这里定义的是**永久对象 key**，不含 presigned URL | agent + core.storage + core 各模块 |
| `result.py` | agent **回传结构化结果**（小 item）+ 工件指针列表 + 执行摘要（耗时、条数、告警） | agent + core |
| `monitor.py`（2026-07-04 增） | **监控/遥测 schema**：节点状态快照（在线状态、槽容量/占用、在途任务清单）、队列统计（各优先级/分组深度）、批次进度（总数/成功/失败/进行中/百分比）、限流调频状态（各出口×域当前速率） | apps/server 监控 API + 前端（经 OpenAPI 共享形状，见下方说明） |
| `event.py`（预留） | 任务生命周期事件、审计事件的形状（血缘/可观测用） | core |
| `version.py` | **契约协议版本号**；agent 连接时握手校验，主控可拒绝过旧/过新的 agent，给出升级提示 | agent + 主控 |
| `errors.py` | **负数错误码枚举 `ErrorCode`**：`requests.state` 负数态与 result/agent 错误帧统一引用的错误码定义 | core + agent + 主控 |
| `enums.py` | **跨模块共享枚举** `RequestState / Channel / Priority / RuleStatus` 等（避免魔法值散落各模块） | core + agent + 主控 |

> **契约增补（2026-07-05，随 11/09/01 轮）**：`agent.py` 注册帧增 **能力标记**（是否支持自动化）；`task.py` 增 **代理配置引用** + **分发分组 `group`**；`result.py` 执行摘要增 **数据质量计数**（解析成功/失败/空白条数）；`monitor.py` 增 **数据质量指标**（解析成功率/失败率/空白率）与代理出口统计。

**边界纪律（这些东西不属于 contracts）**：

- ❌ 不含 SQLAlchemy 模型 / 建表语句（那是 core 的持久化细节；contracts 只描述「传输/交换」的形状，DB schema 可以与之不同）。
- ❌ 不含任何 I/O（不连 DB、不发 HTTP、不读文件）——纯数据类 + 校验 + 枚举。
- ❌ 不含密钥、presigned URL 这类**临时凭据**（它们是运行期产物，不是协议的一部分）。
- ✅ 依赖只有 pydantic（可能加 pydantic 生态的小工具），保证 agent 侧安装轻。
- ✅ **契约变更走版本号**：新增字段尽量向后兼容（可选带默认值），破坏性变更升协议版本，agent/主控握手时校验。

**前端与 AI 如何消费 contracts（2026-07-04 澄清；2026-07-05 随 06 SSR 定案修订）**：contracts 是 Python schema 包，**不提供接口、前端也不 import 它**。链路是：contracts 的 Pydantic 模型作为 FastAPI 端点的 request/response model → FastAPI 自动生成 OpenAPI（`/openapi.json`，含全部 JSON Schema、字段描述与示例）→ ①**AI 直读 openapi.json**（机器可读接口文档天然就绪）；②对外 Dataset API 调用方 / 未来 Python SDK 取类型；③人类看 Swagger UI（`/docs`）/ ReDoc。由此的纪律：**contracts 模型的 Field description/示例要认真写**——它同时喂给 Swagger 文档、AI 与对外 SDK。**（注：06 已定服务端渲染，前端由 Jinja 模板直接消费 core 数据，原「openapi→前端 TS 类型生成」已取消。）** 监控接口本体在 apps/server（monitor.py 只定义数据形状）；前端实时推送通道 = **SSE**（06 定案）。

## 3.8 架构红线（2026-07-05 汇总，汲取点⑦；开工对照防跑偏）

新方案基本已遵守；集中列出便于 CI / 评审对照（借鉴旧方案精华红线）：

| 红线 | 原因 | 新方案落点 |
|---|---|---|
| API 请求不得直接跑爬虫 | 长任务拖垮控制面 | 任务经队列 + agent 执行（07） |
| 用户/AI 代码不得直连 DB | 凭证泄露/越权/拖库 | 沙箱 + Query Gateway 取数（04/04A） |
| 外部采集不得超出授权与站点规则 | 造成合规、授权和审计风险 | 只接入有权访问的数据源；遵守服务条款、API 文档、`robots.txt` 与速率限制；`401/403` 或交互式验证触发暂停和人工复核（01/07/11） |
| 大对象不得进 Redis/WS/HTTP JSON | OOM / 队列膨胀 | 对象存储直传 + 回传指针（01） |
| raw 必须留存（可配开关） | 规则修复后重解析 | raw 存档 zst（02） |
| Connector/规则/组装/推送 必须版本化 | 回滚/灰度/审计/重跑 | 内容寻址 + 状态机（01/02/04/05） |
| AI 生成物不得直接上线 | 必须验证 | test 通道试跑 + 管理员签名（02/08） |
| **契约字段必须诚实** | 不给「已支持」错觉 | **contracts 字段标注「已生效/未生效」**（汲取点⑦） |
| 凭证按风险分层、脚本不接触明文 | 泄密/权限扩散 | 三层凭证 + token 存 hash + 管理员统一（03/05/08） |
| 默认开启 TLS 校验 | 中间人风险 | 默认开，特例显式放行 |

**三类出网画像（出网不变量显式登记，2026-07-07）**：出网只经受控出口，按场景分三类——①**组装/清洗沙箱**：仅可达 **Query Gateway / LLM Gateway**（走**专用 docker network**、**非 `--network=none`**，因沙箱须访问网关）；②**抓取沙箱**：仅经**代理中转**出网（`HTTP_PROXY` 固定入口，不得旁路直连）；③**推送**：**不进沙箱**，由主控**受控执行器**出网，目标域走**白名单**。

## 5. 遗留问题

- HTTP 客户端已定 **niquests**（httpx 停滞出局，见 §2.1）——本条为历史背景，非遗留。
