## 1. 需求对齐

### 1.1 需求方口述（第 1 轮，2026-07-05）

1. **威胁模型定调**：沙箱就是给用户执行代码用的——**即使代码有问题、出错了，也不至于把机器跑崩溃**（= 防事故，不是防恶意逃逸）。
2. **性能担忧**：数据任务中的代码如果都打到沙箱去执行，会不会有性能问题？如何解？
3. **链路担忧**：任务发给 agent、agent 再去调用沙箱——这个链路会不会有风险？

### 1.2 研判（2026-07-05，按此记案、有出入指出）

1. **威胁等级 = 防事故** → 隔离档位定案：**v1 = 容器 + cgroup（内存超限 OOM kill / CPU 配额）+ 常驻 worker 进程池**；nsjail/gVisor 作为可选加固档不默认上；Firecracker 不做。与 §2.1 调研倾向一致。
2. **性能问题三招消解**：
   - **大头根本不进沙箱**：声明式 JSON 规则（工具箱组合的清洗、字段提取）由**内置解释器在 agent 本地跑**——它不是任意代码，无需隔离；只有 Python 脚本才进沙箱（AI 帮写会让脚本变多，但由 sidecar 随机器横向扩展承载，见 §1.3-1）；
   - **按批不按条**（02 已定）：一个批次一次沙箱调用，往返开销摊薄到千百条数据上；
   - **常驻进程池**：沙箱 worker 预热常驻（python 进程复用），无每次冷启动。
3. **链路风险成立，解法 = 就近 sidecar，否决中心沙箱**：
   - 若沙箱是中心服务：agent 抓到的数据要**绕路发到中心沙箱再拿回**——网络多两跳、批数据过网、沙箱挂了全网 agent 脚本执行停摆（单点）。担忧完全成立；
   - **定案方向：沙箱就近部署**——agent 侧脚本用 **agent 同机 sidecar 沙箱**（docker compose 里跟 agent 一起起，调用走 localhost，数据不出机器、零网络风险）；主控侧的组装/推送脚本用**主控旁的执行器**。「代码执行器」接口抽象（02 已定）天然覆盖三形态：本地进程 / 本机 sidecar 沙箱 / 远程沙箱——部署时按机器条件选；
   - 未部署 sidecar 的 agent 机 = 本地执行降级（02 已定），威胁模型既是防事故，本地执行 + 子进程资源限制（超时/rlimit）也是可接受档位。
4. **推送组件的出站**（05 挂来的第 7 问）：推送组件**不进沙箱**、在**主控受控执行器**跑；~~出站按组件配置的目标地址即可、不需要 egress 硬白名单~~ **已被 §4-9/SDD 收口取代**——出站按**目标域白名单 + 加密凭证 + 审计**受控放行（Query Gateway 的 token 机制管的是数据面权限，与此处网络管控是两回事）。

## 2. 技术调研

> 初探核验 2026-07-04（详细选型待威胁等级定后深入）。

### 2.1 隔离技术梯度

- **业界共识：Python 无法语言层沙箱**——解释器高度可内省（对象图、frame、traceback 可达内核对象），RestrictedPython 类方案历史上反复被逃逸；必须 OS 级隔离（github.com/restyler/awesome-sandbox、社区笔记）。
- 隔离梯度（弱→强）：

| 方案 | 机制 | 开销 | 现状 |
|---|---|---|---|
| 容器 + cgroup | namespace + 资源限额 | 最低 | 基线；防资源失控足够，防恶意逃逸不足 |
| **nsjail** | namespace + seccomp-bpf 系统调用过滤 + cgroup | 极低 | Windmill 等生产在用，适合「基线+加固」 |
| 容器 + **gVisor** | 用户态内核截获 syscall | I/O 开销 10–30%，启动快 | Google 出品，容器工作流无缝 |
| **Firecracker** microVM | 独立客户机内核（KVM） | ~125ms 启动 / ~5MiB | 最强隔离，AWS Lambda 底座；对本场景疑似过度 |

- **本项目倾向**（待威胁等级拍板）：脚本经管理员签名、非公开不可信代码 → **v1 = 容器 + cgroup 基线，nsjail/gVisor 作为可选加固档**；Firecracker 仅在未来多租户/执行外部代码时再评估。
- 注意：nsjail/gVisor/Firecracker 均为 **Linux 技术**——沙箱是生产（Linux）形态；Windows 开发机无沙箱 = 走「本地执行」分支（02 已定的降级路径天然覆盖）。

### 2.2 通信与吞吐（待展开）

- 待调研项：worker 常驻进程池 vs 每批新进程（启动开销 vs 状态隔离）；批大小与内存水位的关系。

## 4. 定案（2026-07-05 第 1 轮，详见 [决策记录.md](决策记录.md)）

1. **威胁模型 = 防事故不防恶意**（用户代码写错不拖垮机器）。
2. **隔离档位 v1 = 容器 + cgroup + 常驻 worker 进程池**（nsjail/gVisor 可选加固；Firecracker 不做）。
3. **拓扑 = 就近 sidecar，不做中心沙箱**：agent 同机 sidecar（localhost、数据不出机）；主控旁执行器跑组装/推送脚本；无 sidecar 则本地执行降级。
4. **声明式 JSON 规则不进沙箱**（内置解释器 agent 本地跑）；脚本按批调用 + 进程池免冷启动。
5. **推送组件在主控侧执行器跑**，出站按组件配置目标。
6. **脚本仅 Python，js 去除**（2026-07-05）；AI 写的抓取脚本同样进沙箱，容量由 sidecar 随 agent 机器横向扩展消化。
7. 主控侧沙箱可**单独机器部署**：容器 = worker 池，一个容器起步、不够加容器再加机器；主控配置**沙箱端点列表**、按空闲派发（详见 [09](09-部署运维.md)）。
8. **沙箱 LLM Gateway（汲取点③，2026-07-05 纳入）**：沙箱 egress 除放行 Query Gateway 外，**再放行一个 LLM Gateway**——组装/清洗脚本可 `ctx.ai()` 调 AI（AI 清洗/分类/抽取），**key 留平台侧** + 审计与成本记录 + 结构化输出校验；沙箱仍不能访问任意外网。
9. **执行器与出网口径（2026-07-05 SDD 收口回写）**：生产默认 **`SandboxExecutor`**，**`LocalExecutor` 仅开发/无沙箱降级**（脚本已管理员签名、防事故语境可接受），部署开关默认关。**出网两类分离**：①沙箱脚本(组装/清洗) egress 仅 Query/LLM Gateway；②**推送组件不在沙箱**、在主控受控执行器跑，按目标连接器出网 + 目标域白名单 + 加密凭证 + 审计。

## 5. 从零搭建沙箱实操指南（2026-07-05 新增，供上手 + 瓶颈评估）

> 目的：先跑通、感受一遍，评估瓶颈。命令依据 Docker/gVisor/nsjail 官方规范（gVisor 官方安装页本次抓取超时，以 [gvisor.dev/docs/user_guide/install](https://gvisor.dev/docs/user_guide/install/) 最新为准）。

### 5.0 环境前提（**先看这条，最大的现实约束**）

**所有强隔离技术（gVisor/nsjail/Firecracker）都是 Linux only**——Windows 开发机没有原生 gVisor/nsjail。所以：

| 环境 | 沙箱形态 |
|---|---|
| **Windows 开发**（你的主力机） | Docker Desktop(WSL2) 普通容器 + cgroup 限制（**无 gVisor 加固**）；或直接**本地执行降级**（04A 定的、脚本已签名可接受） |
| **Linux 生产** | Docker + **gVisor(runsc)** 或 **nsjail** 加固 |

→ **结论**：开发期在 Windows 把「容器 + cgroup + 断网」跑通即可；gVisor/nsjail 加固是 Linux 生产的事，本地执行降级兜底无沙箱场景。**别在 Windows 上折腾 gVisor**（Docker Desktop WSL2 理论能跑 runsc 的 systrap 平台，但 KVM 平台要嵌套虚拟化、性能差不推荐——不是开发重点）。

### 5.1 档位一：Docker + cgroup（v1 基线，跨平台，先上手这个）

**① 装 Docker**：Windows → 官网下 **Docker Desktop**（含 WSL2 后端）；Linux → `curl -fsSL https://get.docker.com | sh`。

**② 建执行镜像**（预装运行时，`deploy/sandbox.Dockerfile`）：
```dockerfile
FROM python:3.14-slim
RUN pip install --no-cache-dir pandas polars pyarrow jianbing-utils   # + 爬虫框架/固定方法 SDK
RUN useradd -m sandbox
USER sandbox                    # 非 root 运行
WORKDIR /work
```
`docker build -t payipa-sandbox:latest -f deploy/sandbox.Dockerfile .`

**③ 跑一个脚本的最小命令**（把不可信/签名脚本关进限制里）：
```bash
docker run --rm \
  --network=payipa-sandbox-egress \  # 专用 docker network：唯一可达端点=Query/LLM Gateway（组装/清洗脚本）；真正零网络脚本才用 --network=none；抓取脚本改走代理中转，见下
  --memory=512m \           # 内存上限，超即 OOM kill
  --cpus=1 \                # CPU 配额
  --pids-limit=128 \        # 防 fork 炸弹
  --read-only \             # 根文件系统只读
  -v "$PWD/code:/code:ro" \ # 脚本只读挂入
  -v "$PWD/out:/out" \      # 结果写出目录
  payipa-sandbox:latest \
  python /code/script.py
```
**自己感受瓶颈**：故意写 `while True: pass`（吃 CPU）或 `x=[0]*10**9`（吃内存）跑上面命令，看被 cgroup 限制/OOM kill——这就是「防事故」的效果。
**Python 坑**：容器内 Python 默认看到宿主全部内存，可能超额分配被 kill——cgroup v2 + 合理 `--memory` 即可（生产镜像可设 `PYTHONMALLOC`/内存感知）。

### 5.2 档位二：gVisor(runsc)（Linux 生产加固）

**装**（Debian/Ubuntu，官方 apt 源）：
```bash
curl -fsSL https://gvisor.dev/archive.key | sudo gpg --dearmor -o /usr/share/keyrings/gvisor-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/gvisor-archive-keyring.gpg] https://storage.googleapis.com/gvisor/releases release main" | sudo tee /etc/apt/sources.list.d/gvisor.list
sudo apt-get update && sudo apt-get install -y runsc
sudo runsc install            # 自动写 /etc/docker/daemon.json 注册 runsc runtime
sudo systemctl reload docker
```
**用**：`docker run` 加 `--runtime=runsc`，其余同 5.1。
**平台**：VM 里跑用 **systrap**（默认、性能好）；裸机可用 **kvm**（VM 内需嵌套虚拟化、不推荐）。
**开销**：I/O 密集 10–30%；我们沙箱是 **CPU/解析型**（数据加工），影响有限。

### 5.3 档位三：nsjail（更轻，无容器运行时，Linux）

**装**：`sudo apt-get install -y autoconf bison flex gcc g++ git libprotobuf-dev libnl-route-3-dev libtool make pkg-config protobuf-compiler && git clone https://github.com/google/nsjail && cd nsjail && make`（或 `docker build -t nsjail .`）。

**用**（namespace + cgroup + seccomp，示例）：
```bash
./nsjail \
  --cgroup_mem_max $((512*1024*1024)) \   # 512MB
  --cgroup_pids_max 32 \
  --cgroup_cpu_ms_per_sec 800 \           # 0.8 CPU
  --chroot /srv/jail --user nobody --time_limit 30 \
  -- /usr/bin/python3 /code/script.py
```
也有 `python-nsjail` 包可编程调用。**Windmill 生产即用 nsjail 跑 Python**（[nsjail.dev](https://nsjail.dev/)）。注意：seccomp 策略按语言定——**我们只 Python（js 已去），单一策略**；开发用 `--seccomp_log` 迭代。

### 5.4 平台侧最小 executor（`SandboxExecutor` 怎么调）

```python
# 最小演示（真实版用常驻 worker 池 + Query Gateway 取数、按批不按条）
async def run_in_sandbox(code_dir, out_dir, mem="512m", cpu="1", timeout=1800):
    cmd = ["docker","run","--rm","--network=payipa-sandbox-egress",  # 专用网:唯一可达=Query/LLM Gateway；真正零网络脚本才用 --network=none
           f"--memory={mem}", f"--cpus={cpu}", "--pids-limit=128","--read-only",
           "-v",f"{code_dir}:/code:ro", "-v",f"{out_dir}:/out",
           "payipa-sandbox:latest","python","/code/script.py"]
    with anyio.fail_after(timeout):                 # 硬超时 = 任务租约
        result = await anyio.run_process(cmd, check=False)
    return read_json(out_dir / "result.json")       # 或 stdout JSON
```
- 抓取脚本：额外注入 `HTTP_PROXY/HTTPS_PROXY` 环境变量指向代理中转（旧代码零改造走中转，[12](12-爬虫框架与接入.md)）。
- 数据进出：读走 **Query Gateway（Arrow 流）**；**产物不由沙箱直传对象存储**——脚本把 parquet 写到**共享本地路径**（挂载的 `/out`），由**同机 sidecar 宿主**（非受限 netns）执行 **presigned PUT** 上传对象存储、回指针，**对象存储密钥不入沙箱**；不挂大数据卷。

### 5.5 瓶颈与对策（**你最关心的**）

| 瓶颈 | 说明 | 对策 |
|---|---|---|
| **冷启动**（最主要） | 每任务新起容器 ~几百 ms–秒级 | **常驻容器 worker 进程池**（容器长驻、池内进程复用，04A 定）+ **按批不按条**——摊薄到一批数据上 |
| gVisor I/O 开销 | I/O 密集 10–30% | 我们负载 CPU/解析型，影响小；数据经 Query Gateway 一次性给 |
| **Windows 无 gVisor/nsjail** | 开发机限制 | 开发用普通容器 / 本地执行降级；加固只在 Linux 生产 |
| 内存/CPU 抢占 | 多 worker 争机器 | cgroup 硬限 + worker 池大小 = f(核数/内存) |
| 通信开销 | 频繁小调用拖吞吐 | 按批不按条 + Arrow 流 + 常驻池 |
| seccomp 策略维护 | 各语言 syscall 不同 | 只 Python，单一策略，`--seccomp_log` 迭代 |
| 数据搬运 | 脚本要大量数据 | Query Gateway 读 + parquet 写，不走大数据卷/不进控制面 |

**总结**：主要瓶颈是**冷启动**，靠「常驻 worker 池 + 按批」解决；gVisor 开销对我们负载可接受；Windows 开发用降级。**几十节点规模内无硬瓶颈**——真正要压测的是「常驻池并发 + Query Gateway 吞吐」（POC §13-8）。

### 5.7 控制面协议骨架（`SandboxExecutor` ↔ worker 池，2026-07-05 新增）

> 数据面走 Query/LLM Gateway（Arrow 流）+ 产物 sidecar 上传（§5.4）；此处只定**控制面**四帧，与 [07 §定案-12](07-任务与调度.md) 的任务租约对接。传输 = 本机 unix socket / HTTP（sidecar 同机、走 localhost）。

- **submit**：`SandboxExecutor` 提交一批 → `{task_id, batch_id, attempt_id, code_hash, 入参指针, lease_deadline}`；worker 池按空闲槽派发（端点列表见 [09](09-部署运维.md)），返回 `accepted{worker_id}` 或 `busy`（无空闲槽，退回主控重排）。
- **poll**：按 `attempt_id` 取进度/结果 → `running` / `done{产物指针}` / `failed{负错误码}`；产物只回指针，不进控制面（架构红线：大对象走对象存储）。
- **cancel**：按 `attempt_id` 立即取消（对接 07「取消 = 立即」语义）——worker 对该 attempt 起 anyio `CancelScope` 整树取消、优雅收尾回传已成部分。
- **heartbeat**：worker 周期上报 `{worker_id, 在途 attempt 清单, 空闲槽数}`；主控据此**续租**在途 attempt 的 `lease_deadline` 并做**在途对账**（清单与主控记录不一致 → 判任务丢失、走 07 租约回收）；心跳超时过宽限期则该 worker 在途 attempt 重新入队。
- **租约对接**：`lease_deadline` 由 07 任务租约派生；worker 侧再包 anyio 硬超时（`fail_after`，§5.4）兜底，双保险防卡死。
