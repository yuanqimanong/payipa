## 1. 需求对齐

### 1.1 需求方口述（第 1 轮，2026-07-04）—— 对 8 问的逐条回答

1. **任务来源**：任务数据源存 PostgreSQL，有一张 **cron 调度大表**；触发方式 v1 **全都要**（手动单次 / cron 周期 / 一次性定时 / API 触发）。
2. **任务粒度 = 两层模型**：
   - **站点任务（用户视角的「一个任务」）**：用户配置一个网站规则——放入一堆网址，每个网址可对应各自规则，也可用一条统一规则匹配同一种页面版型；另有向下爬行规则等。这整体算一个任务。
   - **请求数据任务（系统调度单元）**：系统调度站点任务，分发到 agent 执行「下载 + 解析」，这一级叫请求数据任务。
   - agent 解析完成后产生**分流**：结构化数据入库，或解析出的新链接生成新请求任务（**并入同一批次**、继续爬行；批次边界以 §4-6 为权威）。
   - **遍历策略可配**：广度 / 深度，配置页面可选，**默认广度**——广度可以看到总任务量，但数据显示较慢。
   - 底层实现意向：**trio 框架 + 一个可靠的时间调度库**（现状与生态兼容 → §2.1、§2.2）。**最终定案 = anyio + APScheduler（见 §1.3-1/4）。**
3. **状态机**：状态集合全要（排队 / 已分派 / 运行中 / 成功 / 失败 / 已取消 / 超时 / 节点失联）；失败重试策略**任务级可配 + 全局默认**两者都要。
4. **并发与限流**：按**多级站点（多层域名）**控制出口频率——`www.xxx.com`、`news.xxx.com`、`good.news.xxx.com` 这样分别控制，**默认 10**；要**自动调频**功能——根据响应体返回的数据时长调节（需求方点名调研：这样准不准、会不会受代理影响 → §2.3）。
5. **队列载体**：**引入 Redis** 作运行时队列，形态为**有序优先级队列**；未配置 Redis 时降级为**进程内存队列**；**PostgreSQL 记录权威状态**——防任务丢失，支持断点续传、暂停 / 继续。
6. **超时与取消**：任务级超时靠用户配置，默认 **30 min 无进展**；失败次数最大值等可配；请求任务做基本的失败重试（同第 3 条状态机所述）。**任务有批次概念**；取消语义 = **立即**，清空队列中那批任务；在途部分**优雅收尾、回传已抓部分**。
7. **节点分配**：**自动均衡 + 可配置权重**。
8. **任务界面**：全都要（状态、进度百分比、实时日志滚动、产物预览；重跑 / 取消 / 复制新建 / 查看血缘）。

### 1.2 需求对齐（第 2 轮，2026-07-04）—— 澄清回答

1. **trio 必要性**：需求方进一步描述场景——「接收 pyp-agent 的 WS 连接、下发调度任务、用户取消任务时需要立即清掉相关执行单元，单这块用 trio 是不是更好？有必要吗」。助手研判见 **§2.1「取消场景研判」**：取消语义正是结构化并发的用武之地，但 **anyio 在 asyncio 上提供 trio 同款能力**（task group / cancel scope），无需更换事件循环——**待需求方确认走 anyio 路线**。
   - 顺带澄清一个概念：**payipa-contracts 不运行任何服务**，它是纯 Pydantic schema 包（无 I/O，见 [00 §3.6](00-总纲与全局约束.md)）。接收 agent WS 连接的端点在 **apps/server**；下发/调度逻辑在 **payipa-core 的 crawl 模块**；contracts 只定义两边共用的消息形状。
2. **限流**：✅ 拍板——**10 请求/秒**（不是并发数），目标是尽量可控地访问对方 API；**每个完整子域名各自独立配额**；**用户界面可改**。
3. **分流位置**：agent 解析出「数据 + 新链接」回传主控（确认）。需求方问接收方是 core.crawl 还是 contracts——同上澄清：接收端 = apps/server 的 WS 端点（按 contracts 里的帧 schema 解析），随后调用 core.crawl 的分流逻辑（入库 / 生成新请求任务入队）。**模块划分详图需求方稍后专门定**（→ §1.3-③）。
4. **取消语义**：✅ 确认——队列中该批未执行任务立即清除 + 在途（正在 agent 上执行的）请求优雅收尾、回传已抓部分。
5. **批次**：✅ 确认——批次 = 用户前端任务管理中的那个任务（可选定时或一次性）的**一次完整执行轮**；完整一轮就是一批；重跑即新批次。
6. **队列重建**：✅ 确认——无论 Redis 还是内存，崩溃丢队列可接受；PG 任务表记录状态（如 `0=未开始 / 2=进行中 / 1=完成` 之类），据此拉起丢失的任务继续执行。设计纪律随之成立：**队列内容永远可由 PG 重建，队列只是可再生的运行时视图**。
7. **自动调频**：需求方意向——**一开始不要频率太高（慢启动）**，根据对方服务器状态（可能是性能差、也可能是有防护）与 **HTTP 状态码数量**动态调整速度；要求先调研优秀项目怎么做、再结合经验讨论 → 调研见 **§2.5**，设计草案供下一轮讨论。（Google 抓取速率官方文档访问失败，按需求方指示跳过。）

### 1.3 需求对齐（第 3 轮，2026-07-04）—— 拍板

1. **anyio ✅**：并发底座定为 anyio（asyncio 事件循环 + trio 式结构化并发 API），主控与 agent 两侧统一用 task group / cancel scope 组织并发与取消；不引入 trio 事件循环。
2. **自动调频 ✅**：按 §2.5 设计草案执行（(出口×子域) 维度、慢启动、乘性减、封禁分流、弱信号、熔断；v1 先做三件套）。
3. **模块划分**：待定——等讨论到具体模块时再定，不提前画。
4. **时间调度 = APScheduler + 自研 ✅**：APScheduler 3.x 只做「到点触发」；任务分发/队列/状态推进为自研循环。配套设计：cron 定义的权威在 PG 调度大表，调度器启动全量加载 + 变更重载，**不使用 APScheduler jobstore 持久化**（避免与 PG 大表双权威）。

### 1.4 需求对齐（第 4 轮，2026-07-04）—— 收尾回答

1. **限流执行位置：主控 ✅，并定下发流控设计**：
   - 需求方补充的关键点：下发快而 agent 少/代理慢时，任务会在 agent 端堆积——**agent 不做本地缓存队列**（缓存会让部分任务卡死在 agent 端回不来）；需要反馈主控的渠道与检测机制；agent 并发执行单元有 N 个，N 按部署机器配置智能默认，连通后可人工配置。
   - 整理为**槽位信用制（credit-based）流控**：agent 注册时上报并发槽容量 N（按机器规格算默认值，UI 可改）；主控只在 agent 有空闲槽时下发（该 agent 在途任务数 ≤ N），agent 侧不存在任何排队；反馈渠道 = 状态帧/心跳携带在途任务清单与空闲槽数。
   - 检测机制三层（同时回答第 6 条的「卡死」担忧）：①主控给每个已下发请求任务记**租约**（下发时刻 + 预期最长时长，超时即标记并重新入队/判失败）；②agent 端每个抓取协程包 **anyio 超时取消范围**（硬超时，协程不会无限卡住）；③**心跳对账**——agent 上报的在途清单与主控记录不一致（如 agent 异常重启后丢任务）即判「任务丢失」，走租约回收。
   - 术语澄清：N 是**异步并发槽**（协程数），非 OS 线程；网络型抓取 N 可高于 CPU 核数。
2. **优先级 ✅**：来源 = 用户在任务页面配置（高/中/低，默认中），高优先级插队。v1 **单队列**；「多队列 = 按 agent 集群（分组）划分、任务定向发某集群」作为性能扩展方向，归 agent 部署管理讨论。助手评估：方向可行——与 01 已定的「节点分组」（test/prod）同构，TaskSpec 与队列键预留 `group` 字段即可平滑扩展，当下成本极低。
3. **节点分配算法（需求方委托助手评估：加权轮询 abacabac vs 权重×空闲容量）**：**结论 = 按空闲槽位分发**——在有空闲槽的 agent 中选空闲槽最多者，平手轮询。理由：槽位制下**容量即权重**，a:10 / b:5 / c:5 全忙时分配比例自然趋近 2:1:1，稳态与加权轮询等效；但当某 agent 变慢（代理慢/任务重）时其槽位持续被占、自动少派，**自带背压自适应**；纯加权轮询是静态的，会把任务派给「轮到但正忙」的节点——恰好制造第 1 条担心的堆积。即：稳态等价、异常态严格更优。
4. **失联处理 ✅**：按建议——心跳超时后宽限期（默认 3 min 可配）等重连续传；超过则该节点在途请求任务标记「节点失联」重新入队，不计入业务重试次数。
5. **暂停语义 ✅**：暂停 = 停发新请求任务、在途跑完正常回传、队列保留；继续 = 恢复分发。
6. **「无进展」定义 ✅**：批次内 30 min 无任何请求任务状态推进。需求方追问：「没返回也没发出、但完成数量对不上——agent 卡住任务的情况存在吗（理论应该超时）」——**存在**（挂起的抓取、半开连接、agent 异常重启都会造成），由第 1 条的三层检测兜底：任务级租约保证「卡住」在有限时间内必转为超时/重入队；批次级 30 min 无进展是最后一道保险；且 PG 逐请求任务记状态，完成数恒可由 PG 对账，不会静默对不上。
7. **重试默认值 ✅ + 自定义失败判定**：默认 3 次、指数退避+抖动，429/503 跟随调频器（Retry-After 优先）。另定：**页面提供用户自定义失败判定配置**——HTTP 200 但响应内容含特定特征（如错误提示文案）也可判为失败（「软失败」），此类失败重试时**优先更换代理出口**（部分错误页换出口即恢复；与 §2.5-④ 封禁分流的内容特征检测共用机制）。

## 2. 技术调研

> 事实核验于 **2026-07-04**（PyPI JSON API、官方文档、GitHub issue，一手来源）。

### 2.1 trio 现状与生态兼容（针对口述②的选型意向）

**trio 本身健康，但本项目已定技术栈整体是 asyncio 系，真 trio 事件循环会失去几乎全部已选依赖。**

- **trio 0.33.0**（2026-02-14），`requires-python >=3.10`，classifier 含 3.14；自述「成熟、良好测试、生产广泛使用、破坏性变更罕见」，但 PyPI 分级仍标 Beta（接口偶有微调）。（pypi.org/pypi/trio）
- 与已定/主流栈的兼容矩阵：

| 组件 | asyncio | trio | 备注 |
|---|---|---|---|
| uvicorn（ASGI 服务器） | ✅ | ❌ 不支持 | trio 须换 **Hypercorn**（支持 asyncio/trio 双 backend）（fastapi.tiangolo.com、GitHub fastapi discussion #7299） |
| niquests（HTTP 客户端，00 已倾向） | ✅ | ❌ 仅 asyncio | 官方文档明说 async 后端只支持 asyncio，欢迎 anyio 贡献（niquests.readthedocs.io） |
| websockets 16.x（01 已定 agent WS 库） | ✅ | ❌ | trio 侧替代 trio-websocket 0.12.2（2025-02），自述 **life-support 维护状态**（pypi.org/pypi/trio-websocket） |
| redis-py 8.0.1 | ✅ 原生 async | ❌ 无 trio 客户端 | classifier 含 3.14（pypi.org/pypi/redis） |
| SQLAlchemy async / asyncpg | ✅ | ❌ | asyncio 专属（既有知识，未单独核验） |

- **调和路径：anyio 4.14.1**（2026-06-24，classifier 含 3.14）——官方定位即「在 asyncio 之上实现 trio 式结构化并发，并与 trio 原生 SC 和谐工作」；**FastAPI/Starlette 本身构建在 anyio 上**。含义：想要 trio 的结构化并发范式（task group、取消范围、超时块），在 asyncio 事件循环上用 anyio 即可获得同款 API，同时保住全部 asyncio 生态。（pypi.org/pypi/anyio）
- 三条路线：**A. anyio on asyncio**（零生态损失）；B. 真 trio 循环（换 Hypercorn + 换 HTTP 客户端 + life-support 的 WS 库 + 无 Redis 客户端——工程上不推荐但如实列出）；C. 调度器拆独立 trio 进程（多一个常驻进程与 IPC 复杂度）。

**取消场景研判（第 2 轮补充，回应 §1.2-1）**：

- 取消的对象是**协程任务树，不是线程**——「立即清掉相关执行单元」= 取消一批 in-flight 协程（主控侧：该批任务的调度/等待协程；agent 侧：抓取工作协程）。
- 裸 asyncio 做这件事的痛点是真实的：`Task.cancel()` 要逐个追踪、易漏孤儿任务、清理顺序难保证——这正是 trio 结构化并发（nursery/cancel scope，「取消即取消整棵树」）要解决的问题。
- 但 **anyio 在 asyncio 上提供同款语义**：`TaskGroup`（组内任一失败/取消 → 全组取消）、`CancelScope`、`move_on_after/fail_after` 超时块；FastAPI/Starlette 底座就是 anyio，主控侧零额外成本；agent 侧同样可用 anyio 包住 websockets/niquests 的 asyncio 协程。
- 跨机器的「立即取消」本质是 **WS cancel 帧 + agent 收帧后本地取消其工作协程树**——与用哪个事件循环无关。
- **结论（已定，见 §1.3-1）**：结构化并发的取消语义值得要；trio 事件循环没必要——**路线 A（anyio）**，主控与 agent 两侧统一用 anyio task group / cancel scope 组织并发。

### 2.3 基于响应时长的自动调频：准确性与代理影响（需求方点名调研）

**结论：方向正确但单一信号不足；「受代理影响」的担心成立——经代理测得的是代理链路延迟，不是目标服务器负载。业界两大爬虫参照都有公开的失败案例，教训一致：要混合信号。**

- **Scrapy AutoThrottle（响应时长调频的代表实现）**（docs.scrapy.org/en/latest/topics/autothrottle.html）：
  - latency 定义 = **建立 TCP 连接 → 收到 HTTP 响应头**的耗时；目标公式 `download_delay = latency / target_concurrency`；新 delay 与上次 delay **取平均平滑**；**非 200 响应只用于加 delay、不用于减**；受 `AUTOTHROTTLE_MAX_DELAY`（默认 60s）与硬并发上限约束。
  - 文档自认：协作式多任务环境下 latency **很难精确测量**（爬虫忙于处理回调时无法及时收包，测出的时长偏大）——即测量本身就含本机噪声。
- **公开缺陷**：
  1. **完全不看状态码语义**——429/503 限流响应不会触发针对性减速，scrapy issue #4424（Adjust throttling for 429 response codes）至今开放（github.com/scrapy/scrapy/issues/4424）；
  2. **振荡**——一批快页把 delay 压低、随后慢页又抬高，delay 来回摆（dev.to 社区分析）；
  3. **代理影响确认**——经代理时测得的 latency 反映的是「代理链路」而非目标服务器负载；代理池场景各出口延迟不同，混在一起取平均进一步失真（dev.to/extractdata、dev.to/ikram_khan）。
- **Crawlee AutoscaledPool（第二参照，Apify 出品）**（crawlee.dev scaling 指南）：按**本机资源**（CPU/内存/事件循环阻塞）每 10s 调节并发、步长 0.05——另一个极端：只看自己不看目标站。公开 issue #1437 记录了「**死亡螺旋**」：目标站变慢返回 429 → 本机 CPU 反而空闲 → 继续加并发 → 压垮小站（github.com/apify/crawlee-python/issues/1437）。
- 相关既有件：pyrate-limiter（00 就绪表已核验 3.14 就绪）可作限流原语底座；自动调频逻辑属自研层。

### 2.4 Redis 有序优先级队列 + PG 权威状态（口述⑤的可行性）

**该组合是业界成熟模式，可行；关键设计纪律是「PG 为唯一权威，Redis 队列永远可重建」。**

- redis-py 8.0.1：原生 asyncio 支持，classifier 含 3.14（pypi.org/pypi/redis）。
- 优先级队列载体：**sorted set + ZPOPMIN/BZPOPMIN**——按 score（优先级/时间戳）原子弹出，阻塞变体适合 worker 等待；Redis 官方 job queue 文档同款模式（redis.io/docs job-queue、oneuptime.com 系列模式文）。
- 可靠性语义：Redis 侧做至少一次投递需「processing 暂存区 + visibility timeout + 回收器」模式；**但本设计中 PG 记权威状态，Redis 仅运行时队列**——丢失（重启/故障）后从 PG 按状态重建即可，无需在 Redis 层追求持久化（不必上 Streams/AOF 强持久）。这同时天然覆盖「未配 Redis 用内存队列」的降级：两种后端语义一致（都是可再生视图），暂停/继续、断点续传的依据都在 PG。
- 现成参考：SAQ（§2.2）即「Redis/PG 队列 + cron + 心跳回收」的现成组合，评估自研前值得先看其取舍。
- 遍历策略与队列的衔接（设计说明）：广度/深度共用同一优先级队列——三元 score = (优先级档, **按策略正/负的深度项**, 单调入队序)，广度 = 深度升序、深度 = 深度降序，无需两套队列实现；入队序用**秒级或自增序号（非毫秒纪元）**，防 Redis sorted set 的 float64 52 位尾数溢出。

### 2.5 自动调频：优秀项目横向调研（第 2 轮，2026-07-04）

> 应需求方要求的横向调研：优秀项目如何做「动态调速」。Google 抓取速率官方文档访问失败，按需求方指示跳过。以下均为一手来源，核验 2026-07-04。

| 项目 | 调什么 | 依据信号 | 机制要点 |
|---|---|---|---|
| **Scrapy AutoThrottle** | 请求间隔 | 响应延迟 | `delay = latency / 目标并发`，与上次取均值平滑；非 200 只升不降。缺陷见 §2.3（docs.scrapy.org） |
| **Heritrix**（互联网档案馆网页存档爬虫） | 同主机请求间隔 | 上次抓取耗时 | 间隔 = 上次耗时 × `delayFactor`（参考配置 5.0），夹在 `[minDelayMs=3000, maxDelayMs=30000]`——「**对方越慢我越慢**」的比例礼貌，例：上次 800ms → 等 4000ms（heritrix.readthedocs.io） |
| **AWS SDK · standard 重试** | 重试退避 | **错误分类**（错误码优先，HTTP 码兜底） | 瞬时错误基线 50ms vs **限流错误基线 1000ms（20 倍）**，指数退避 + 满抖动，封顶 20s；**尊重服务端 Retry-After 类头**；**retry quota 令牌桶**（500 枚，瞬时重试扣 14 / 限流扣 5，成功返还）——持续失败率超约 22–32% 即熔断快速失败，不再空耗重试（docs.aws.amazon.com/sdkref） |
| **AWS SDK · adaptive 模式** | 发送速率 | 限流响应 | 在 standard 之上加**客户端限速器**：跟踪 throttling 响应动态调低发送速率，必要时连首个请求都延迟；官方明示只推荐单资源、限流频繁的场景（docs.aws.amazon.com/sdkref） |
| **Netflix concurrency-limits** | 并发上限 | 延迟（TCP 拥塞控制思路） | Little 定律 `Limit = RPS × 延迟`；**Vegas**：队列深度估计 `L×(1−minRTT/sampleRTT)`，低于 α(2-3) 则 +1、高于 β(4-6) 则 −1；**Gradient2**：长短两条指数移动平均的背离检测「持续排队趋势」，抗突发抖动；**AIMD**：加性增、乘性减（超时/拒绝触发大幅回退）（github.com/Netflix/concurrency-limits） |
| **Envoy adaptive concurrency** | 并发上限 | 延迟梯度 | `gradient = (minRTT + 缓冲) / sampleRTT`；`limit_new = gradient × limit_old + √limit 余量`；**每 60s 主动压低并发重测 minRTT**（「理想条件采样」，50 样本取 P90）+ 抖动错峰（envoyproxy.io） |
| **Crawlee SessionPool** | **封禁应对（不是调速）** | 状态码 + 页面内容 | session 带 error score：`mark_bad()` 累积、`mark_good()` 回落、超 `max_error_score` 判废；`blocked_status_codes`（403 等）与页面内容特征（如 "Blocked" 标题）判封；确认封禁 `retire()` → 自动换 session/代理重试——**封禁的答案是换出口，不是降速**（crawlee.dev/python session-management） |

**横向规律（设计输入）**：

1. **两类问题、两套机制**：所有成熟系统都把「吞吐调优」（我能跑多快——延迟/并发信号）与「防护应对」（我是不是被限/被封——状态码/内容信号）分开处理。需求方「对方性能差 vs 人家防护了」的直觉正对应这条分界。
2. **状态码按语义分级**，不一视同仁：AWS 把限流类错误单独分类、退避基线放大 20 倍、优先尊重 Retry-After；403/验证码类是封禁信号，走换出口通道而非降速。
3. **慢启动 + 加性增/乘性减（AIMD）是共同骨架**：正常时小步提速，收到限流/超时立即乘性回退——TCP 拥塞控制三十年验证的收敛模式；Netflix/Envoy 的梯度算法是其精细化变体。需求方「一开始不要频率太高」= 教科书式慢启动。
4. **延迟只做趋势信号，且要双重平滑**：Envoy/Netflix 都不用原始延迟——用 minRTT 基线与当前样本的比值、或长短 EWMA 背离；避免 Scrapy 式振荡。且延迟经代理失真（§2.3），只能当弱信号。
5. **持续高失败率要熔断**而非无限重试：AWS retry quota 的 fail-fast 思想——失败率长期超阈值时停止轰击、直接告警。

**结合经验的设计草案（已按此定案，见 §1.3-2 / §4-10）**——落在「上限 10 rps/子域、UI 可改」框架内：

| # | 机制 | 内容 |
|---|---|---|
| ① | 维度 | 限速器实例按 **(代理出口 × 子域名)** 建；不用代理时退化为按子域名。用户配的 10 rps 是**天花板**，调频器在 [下限, 天花板] 区间内工作 |
| ② | 慢启动 | 新域/冷启动从天花板的 10–20% 起步，每个健康窗口（如 30s 无异常）**加性**提速一档 |
| ③ | 强信号 → 乘性减 | **429/503** → 速率立即减半并退避；带 **Retry-After** 头则按头等待（AWS 同款：服务端指示优先）；连续触发 → 指数加深退避 |
| ④ | 封禁信号 → 换出口（不降速） | **403 / 验证码页 / 内容特征** → 该 (出口×域) 标记不可用、换出口重试 + 计入告警（Crawlee retire 模式）——避免「被封了还在傻降速」 |
| ⑤ | 弱信号 → 趋势微调 | 响应时长长短 EWMA 背离持续变差 → 停止提速/小步降速；单独不触发大动作（防代理噪声误伤） |
| ⑥ | 熔断 | 窗口失败率超阈值（参考 AWS 的 ~25% 量级）→ 暂停该 (出口×域) 并告警，冷却后半开恢复 |
| ⑦ | v1 范围建议 | **②③④ 三件套先行**（AIMD + Retry-After + 封禁分流：简单、可解释、覆盖主要风险）；⑤⑥ 次之；Vegas/梯度类算法留作后续精细化参考 |

## 4. 定案（截至 2026-07-04 第 2 轮，详见 [决策记录.md](决策记录.md)）

1. **触发方式 v1 全要**：手动单次 / cron 周期 / 一次性定时 / API 触发；cron 定义存 PG 调度大表。
2. **两层任务模型**：站点任务（用户视角）→ 请求数据任务（调度单元，agent 执行**单次下载+解析**）；解析结果经 `ResultBatch.discovered` 回传主控分流（入库 / **主控对新链接 URL 指纹去重后生成新请求任务入队、并入同一批次**）；agent 无本地队列（D18）、集中限流（红线3）；遍历广度/深度可配，默认广度（广度可见总任务量、数据显示较慢）。
3. **状态机全集**（排队/已分派/运行中/成功/失败/已取消/超时/节点失联）；重试策略任务级可配 + 全局默认。
4. **限流：按完整子域名独立配额，默认 10 请求/秒，UI 可改**。
5. **队列：Redis 有序优先级队列；未配置降级进程内存队列；PG 任务表为唯一权威状态**（如 0=未开始/2=进行中/1=完成），崩溃丢队列后由 PG 重建（断点续传/暂停继续同源）。
6. **超时/取消**：默认 30min 无进展超时（任务级可配）；**批次 = 任务一次完整执行轮**（一次爬行 = 一个批次，解析出的新链接并入同一 `batch_id`、不另起批次）；**批次完成守卫 = 队列空 AND 无在途 AND 无「待处理结果/待发链接」计数**（补该计数防多波爬行提前收尾）；取消 = 立即清空队列中该批 + 在途优雅收尾、回传已抓部分。
7. **节点分配：自动均衡 + 可配置权重**。
8. **任务界面全要**（状态/进度/实时日志/产物预览 + 重跑/取消/复制新建/血缘；页面明细归 06-界面 模块）。
9. **并发底座 = anyio**（asyncio 事件循环 + trio 式结构化并发 API；取消 = task group/cancel scope 整树取消；主控与 agent 两侧统一）。（第 3 轮）
10. **自动调频按 §2.5 草案**：(代理出口 × 子域名) 维度、用户配额为天花板；慢启动 + 加性增/乘性减；429/503 减半且 Retry-After 优先；403/验证码走换出口不降速；时长双 EWMA 弱信号；失败率熔断；v1 先做「慢启动 AIMD + Retry-After + 封禁分流」三件套。（第 3 轮）
11. **时间调度 = APScheduler 3.x（仅到点触发）+ 自研分发循环**；cron 定义权威在 PG 调度大表（启动加载 + 变更重载），不用 APScheduler jobstore 持久化。（第 3 轮）
12. **下发流控 = 槽位信用制**：agent 无本地缓存队列；并发槽 N（机器规格智能默认 + UI 可改）；主控按空闲槽下发（在途 ≤ N）；检测 = 任务租约 + agent 侧协程硬超时 + 心跳在途对账。（第 4 轮）
13. **节点分配 = 按空闲槽位分发**（有空闲槽者中取最多，平手轮询）；容量即权重、自带背压；放弃静态加权轮询。（第 4 轮）
14. **优先级 = 用户任务页三档（高/中/低，默认中）**；v1 单队列，score = (优先级档, 按策略正/负的深度项, 单调入队序)（以 §2.4 为准；入队序用秒级/自增序号防 float64 尾数溢出）；TaskSpec 与队列键预留 `group` 字段供集群分组扩展。（第 4 轮）
15. **失败判定可自定义**：默认状态码语义 + 用户可配「200 + 内容特征 = 软失败」；软失败重试优先换代理出口。（第 4 轮）
16. **agent 分组用于能力分发**（2026-07-05）：`group` 不止 test/prod，也用于**能力集群**（如「自动化集群」——只有装了自动化引擎的 agent）；**数据源规则可下拉选分发到哪个 agent 分组**，需要自动化的任务发给有自动化能力的分组。代理出口选择对接 [11 代理池](11-代理池.md)。
17. **限流维度加 account/profile（汲取点⑤，2026-07-05 纳入）**：限流/调频 key 除 (代理出口 × 子域名) 外，再加**采集账号/凭证**维度——API 型数据源常按账号配额，需按账号独立限流（如 X API）。

待定项见 §1.5；模块划分详图待定（等讨论到具体模块时定）。
