## 1. 需求对齐

### 1.1 需求方口述（第 1 轮，2026-07-05）

1. **日志查看**：有查看各种日志的地方，**运维权限**的用户才可以看。
2. **权限体系 = RBAC**：平台遵循 RBAC 权限管理；可以给某个用户**增加多种角色或特殊权限**（多角色 + 点状特殊授权）；**权限由管理员可配置**。

### 1.2 需求方口述（第 2 轮，2026-07-05）—— 对五问的回答

1. **部署形态**：沙箱单独部署一台机器——一个容器够吗？多个容器如何连接到平台？**PG 单独机器**；**主控单独机器**；agent 打算用 2 台新机器、每台开 10 个不同端口共 20 个 agent，每 agent 线程数默认按机器性能、主控页面可人工改——**是不是推荐一机一 agent？**（→ §1.3-1/2 研判）
2. **日志**：管理员可配保留、**默认 30 天**、存 PG 平台库 `pyp`；**三库：`pyp` = 平台相关表 / `data_center` = 专放采集数据 / `business` = 专放组装后数据**；可观测：基础系统的在前端里做；**AI 可观测外接自部署 Langfuse**。
3. **备份**：不做，靠 pgsql 本身。
4. **升级策略**：需要（→ §1.3-6 草案）。
5. **agent 配置有统一管理界面**。

### 1.3 研判（2026-07-05，按此记案、有出入指出）

1. **一机一 agent：是，强烈推荐**，且先纠正一个误解——**agent 是出站 WS 连接，不监听任何端口**，「每台开 10 个端口」这个维度不存在。一台机器跑 10 个 agent 进程没有收益：agent 的并发能力由**槽位 N**决定（07 已定，进程内异步协程），一个 agent 进程调大 N 即可吃满整机网络能力；10 个进程 = 10 份 WS/心跳/规则缓存开销，还让主控调度视图碎片化（20 个小节点 vs 2 个大节点）。多 agent 进程唯一合理场景：按代理出口/网络命名空间隔离（不同拨号线路各挂一个）——真有需求再开。→ **2 台 agent 机 = 2 个 agent**，槽位 N 默认按机器性能、节点管理页可改。
2. **沙箱单独机器与 04A 的 sidecar 不冲突——两类脚本两种归宿**：
   - **agent 侧脚本**（解析/清洗，含 AI 写的抓取逻辑）→ 仍 **agent 同机 sidecar**（数据不出机；量随 agent 机器横向扩展）；
   - **主控侧脚本（组装/推送拆开归宿）**：**组装/清洗** → **单独网络隔离沙箱机器成立**（egress 仅 Query Gateway）：组装数据本来就经 Query Gateway 过网，沙箱在哪数据路径都一样。**一个容器起步够用**（容器内 worker 进程池并发）；不够先加容器、再加机器。**推送不进沙箱 worker 池** → 由**主控受控执行器出网**（目标域白名单 + 加密凭证 + 审计，明文凭证不入沙箱 worker）；
   - **对象存储兜底**：**S3 未配时主控本地盘 + HTTP 分块兜底**。
   - **多容器/多机接平台**：v1 最简——主控配置**沙箱端点列表**，按空闲派发批任务（复用 07 槽位思想：沙箱上报 worker 池占用）；将来要免配置再升级为出站注册（同 agent join token 模式），v1 不需要。
3. **三库划分（2026-07-05 第 3 轮确认，纠正前一轮误记的「双库」）**：PG 一实例**三库**——
   - **`pyp` = 平台库**：系统表（任务、规则/版型、用户/角色/权限、审计与操作日志、数据源配置、cron 调度大表等全部平台元数据）；
   - **`data_center` = 采集数据库**：各数据源按数据分表的 `data_*` 表（02 定的落这里）；
   - **`business` = 组装产物库**：组装后的新表（04 产物落这里）；
   - 库名安装时可配；日志存 `pyp`、默认 30 天、超期定时清理。
   - **注（跨库限制）**：PG 跨 database 不能直接 SQL join——本设计不需要（03 查询按单表、04 组装是「读 `data_center` → 写 `business`」的应用层跨库），故三库物理隔离可行；若将来需「采集数据 × 组装数据」在 SQL 层联查，再评估改用同库多 schema 或 postgres_fdw。
4. **可观测**：基础系统观测 = 平台自带前端监控页（落在已定的 contracts monitor.py + 监控 API + SSE 上，零新增外部件，不上 Prometheus/Grafana）；**AI 调用观测 = 外接自部署 Langfuse**（SDK 4.13.0，MIT，2026-03 起 v4；开源可自部署，部署细节实现期核验）——平台 AI 调用点埋 Langfuse SDK。
5. **备份 = v1 不做平台内备份功能**（需求方拍板）。**风险注记（必须写）**：PG 自身不会自动备份，库机磁盘损毁即数据全失；最低建议由运维在平台外自行安排定时 pg_dump / WAL 归档——平台文档将来附一页「建议备份命令」，不做进产品。
6. **升级策略草案（待需求方点头）**：
   - **版本三层**：平台版本（server）、契约协议版本（contracts version.py，握手校验已定）、agent 版本；
   - **平台升级**：DB migration 用 **Alembic**（SQLAlchemy 官配迁移工具，实现期核验版本）；流程 = 停服 → 迁移 → 起新版（单实例场景短暂停机可接受）；
   - **agent 升级**：主控握手检测版本过旧 → 节点管理页标「需升级」+ 给出升级命令（`pip install -U pyp-agent` / `docker pull`）→ **人工执行**（v1 不做主控远程下发升级——那是新的远程执行面）；协议不兼容时主控拒连并提示（version.py 既定）；
   - **灰度**：先升测试节点组（01 既定分组）验证，再升生产节点。

### 1.4 需求方口述（第 3 轮，2026-07-05）—— 监控 + 自动化 + 代理

1. **监控（monitor）很重要**：监控 agent、机器、任务成功率/失败率、**字段解析成功·失败·空白率**等。问：放 `payipa-core/agent` 下吗？
   - **纠正**：core 里**没有 agent 模块**（agent 是独立包 pyp-agent、core 不依赖它）。监控是**主控侧聚合**，落 **`core.monitor` 新模块**（§4-9）；agent 只在**结果帧回报原始计数**（解析条数/成功/失败/空白等），统计与聚合在主控 monitor。schema 在 contracts `monitor.py`（补数据质量字段）+ `result.py`（补执行摘要计数），接口在 apps/server，页在 [06 系统监控](06-界面.md)。
2. **自动化 = agent 可选能力 + 分组和引擎能力分发**：归 [01 §4.3](01-数据获取与Agent.md) / [07 §4-16](07-任务与调度.md)；统一使用标准 **Playwright** 处理动态渲染和已授权交互。
3. **网络出口与访问边界**：部署级固定网络配置与整源暂停策略见 [11](11-网络出口与访问边界.md)。

## 4. 定案（2026-07-05，详见 [决策记录.md](决策记录.md)）

1. **权限 = RBAC**：一个用户可授**多种角色 + 特殊权限**；权限管理员可配置；角色集合现为**管理员 / 技术 / 运营 / 运维**。
2. **操作日志（审计）页按权限码 `audit.read` 门控**（非硬编码角色名；管理员默认可见）。**实现现状**：`/audit` 页读 `audit_log`（`/api/views/audit`，支持动作筛选 + 分页）；`/logs` 为纯说明页（指向运行时 structlog 在 stdout / `docker logs` 与审计日志在 `/audit`），无独立 `logs.view` 权限码。
3. **部署拓扑 v1**：单主控、单 worker；PostgreSQL 同实例三库（`pyp_sys` / `data_center` / `business`，库名可配）；若干独立 Agent 出站连接主控。本版对象存储正式支持本地持久卷；S3 与 Redis 尚未接线，配置 S3 会启动失败，不能把规划能力当成已实现能力。
4. **日志（口径）**：ops 日志页的 `pyp` 内日志源规划 = `audit_log` + `task_events`，默认保留 30 天、管理员可配（**30 天为超期定时清理目标**）；**应用/错误 structlog 建议留 stdout / Docker 捕获、不入 PG**（如需入 PG 则显式加日志表 + PG handler，不隐式写库）。**实现现状**：`/audit` 页仅呈现 `audit_log`（动作筛选 + 分页）；`task_events` 作为日志源的页面化聚合尚未实现（规划）。
5. **可观测**：基础 = 自带前端监控页（monitor schema + SSE）；**AI = 外接自部署 Langfuse**。
6. **备份**：`pypctl backup/restore` 冷备/恢复三库、本地对象卷和部署配置，带 SHA-256 清单；每版本仍须在隔离环境做恢复演练。
7. **agent 配置统一管理界面**（节点管理页，归 06 页面清单）。
8. **升级策略**（2026-07-05 采纳草案）：三层版本（平台 server / 契约协议 version.py / agent）；平台升级用 **Alembic** 迁移（停服 → 迁移 → 起新版，单实例短暂停机可接受）；agent 握手检测版本过旧 → 节点管理页标「需升级」+ 给命令（`pip install -U` / `docker pull`）、**人工执行**（不做主控远程下发升级）；协议不兼容主控拒连提示；灰度先升测试节点组再升生产。
9. **监控 = `core.monitor` 模块**（不在 core/agent——core 无 agent 模块）：聚合 agent 在线态/并发槽 / 任务成功率失败率 / **数据质量（字段解析成功·失败·空白率）**；agent 仅回报原始计数，聚合在主控；schema 在 contracts `monitor.py` + `result.py`，接口在 apps/server，页在 06 系统监控。**机器指标（CPU/内存/负载）为预留、当前未聚合**（`Heartbeat.metrics` 标注 reserved，`monitor` 暂不产出）。**节点在线判定 = 状态列 online + `last_heartbeat` 在新鲜期内（默认 90s）双条件**（硬崩溃 agent 的 status 列会永久停留 online，仅看状态列会显示僵尸节点）。

### 4.1 生产安全上线检查（2026-07-11 B 加固）

生产部署置 `PYP_SERVER_ENVIRONMENT=production`，主控启动前置校验（`preflight.py`）会在下列任一不满足时**拒绝启动**（开机即失败，而非静默带病运行）：

1. `PYP_SERVER_RBAC_ENABLED=true`（production 强制；使全部 `require_perm` 端点登录 + 鉴权）。
2. `PYP_SERVER_ALLOWED_HOSTS` 填实际域名/IP，不能使用 `*`。
3. `PYP_SERVER_SESSION_SECRET` 非 dev 默认值且 ≥32 字节（会话 HS256 签名强度）。
4. `PYP_SERVER_BOOTSTRAP_TOKEN` 非 dev 默认值且 ≥24 字节（防空库首个管理员被公开抢注）。
5. `UPLOAD_SECRET` / `CRED_KEK` 非 dev 默认值（内部上传/作业令牌、凭证信封）。
6. Agent 只使用节点页签发的短时单次入网码；production 不接受共享 join token。

dev 模式（默认）保持宽松：JSON API 免登录、允许 dev 默认密钥，仅在 API 开放时打一条启动告警。
另：SSR 状态变更表单（登录/建源/访问复核）在会话 cookie `SameSite=Lax` 之上再加 **CSRF 双提交 token**；
`/api/views/*` 敏感数据端点即便 RBAC 关也强制登录（路由级 `require_user`），与页面外壳登录保护对齐。
