## 1. 结论与总体判断

payipa 的技术主链（建源 → WS 抓取 → raw 归档 → 解析清洗 → 三库入库 → 查询 → 组装 → 推送 → 通知）**端到端真实打通**，且核心不变量（跨库「先数据后状态」顺序、attempt fencing 三重守卫、Outbox SKIP LOCKED 原子认领、动态表标识符校验、沙箱只读根+cap-drop+网关白名单、生产 preflight 硬门禁）实现得扎实且有清晰注释——工程成熟度明显高于一般内部预览版，13 号文 P0 第一批的成果已确实沉淀进代码。

站在未来视角，需要加强的地方可归为四层，按「越晚做、牵动面越大」排序：

1. **少数真实的可靠性 / 正确性缺陷**——现在几乎必然踩中或已在静默发生，修复成本低（见 §2，多为 P0/P1）。
2. **结构性锁死点**——现在不划接口缝、将来是「重写而非替换」的决策：契约兼容窗口、Connector 注册模型、进程内权威态、对外 API 版本前缀（散落在 §2/§3/§9）。
3. **能力已实现但用户触达不到 / 承诺未兑现**——引擎造好了没接油门：M6 韧性与清洗能力无配置入口、数据组装无创作面、AI 网关空转、`ctx.ai()` 文档漂移（见 §5/§9）。
4. **平台化的「向外看」维度**——决定产品天花板但九维评审偏「向内看」而系统性漏掉的：对外集成 API、数据血缘、生态/模板分发、商业化计量与遥测姿态（见 §10）。

> 两条被对抗核查**证伪**的常见误判，特此记录以免后续开发误信：
> - 采集侧 `RulePack.script_ref` **不是**「active 却永不生效的死契约」——它在契约里是 `reserved(...)`，`_annotate` 会给 description 加 `[未生效]` 前缀并置 `x-effective:False`，已如实标注（`rule.py:109`）。
> - Alembic downgrade **并非**「普遍为空导致 schema 不可逆」——平台表迁移（`downgrade_pyp` / `downgrade_data_center` 的 artifacts 等）都有真实 `drop_*` 逆操作；仅 `data_*/asm_*` 运行时动态库对应的 `downgrade` 是 `pass`，而这些表本就不进 Alembic，是**正确设计**（`deploy/alembic/versions/*`）。

## 3. 架构与运行模型：结构性锁死点

主控当前是「单进程、结构化并发」模型，靠 PG advisory lock 强制单实例单 worker——对 v1 正确。真正会锁死演进的不是队列（两条重队列已 DB-backed 幂等，插入点很干净），而是几处**进程内权威态**与**契约刚性**：

- **契约兼容窗口为零（`MIN_SUPPORTED==CONTRACT==4`）**（P1）。`version.py:12-20` 要求对端严格 `==4`，`ws.py:182` 对不匹配直接 close(1002)。这是出于「旧 agent 不回显 attempt 会破坏 fencing」的安全主动决策，但把灰度升级路径关死了：v4→v5 时全部远程 Agent 下次重连即被硬拒、任务停摆。**建议**：破坏性变更时过渡期同时接受 `[N-1, N]`，旧帧走兼容降级；确立「新增可选字段不升版本 / 破坏性字段走 deprecated→双读→下线」的契约演进规程；长期从单调整数版本走向能力协商。（13 §3.7 只跟踪「生成兼容表+注册帧带版本」，未点破窗口为零。）
- **派发环与内存 Hub 紧耦合、Agent 在线态无 DB 影子**（P1→P2）。`scheduler.py:62-94` 的 `drain_once` 直接持 Hub 对象引用同步调 `pick_free/send_frame`，Hub 是 `app.state` 纯内存单例，`agents` 表无 `free_slots/inflight/generation` 投影。将来拆 `pyp-dispatcher` 时，独立进程无法直接 `send_frame`，会被迫「派发与 WS 终结永远绑死」或重写。**建议**：趁调用点只有 scheduler 一处，先立窄接口 `AgentRouter Protocol`（`pick_free/free_caps/send/mark_dispatched`），Agent 在线态低频快照落库，把 §5.2 拆分从「重写」降级为「换实现+加命令通道」。（13 §3.4/§5.2 跟踪了拆分目标，未点破代码层缺接口缝。）
- **新数据源/Connector 类型缺统一注册 seam**（P2）。`ConnectorType` 枚举有 web/api/feed/push/file_db 并存库（`pyp.py:115`），但建源硬编码 `"web"`（`run.py:118`），全仓无按 `connector_type` 分派的消费点；实际行为完全由 `engine_hint` 的 if/elif（`fetch.py`）决定。对照之下 LLM provider（`PROVIDERS` dict）、通知渠道（`_SENDERS` dict）、存储后端（`StorageBackend` ABC）都有干净注册表。**建议**：把已验证的注册表模式推广到「加一种数据源类型」这个最大扩展轴，定义 Connector 抽象 + registry，建源/派发过滤/agent 执行都按 registry 分派。
- **三库共享单 PG 实例、单套凭证**（P2）。`db/settings.py:29-73` 三库共用同一 host/凭证、只切 database 名。`data_center`（体量最大、最先需要独立硬件）的物理外置被配置锁死。**建议**：settings 增加按库可选 DSN 覆盖（如 `PYP_PG_DSN_DATA_CENTER`），缺省回落共享；把跨库「先数据后状态、幂等收敛、单向不变量」写入架构/排障文档（避免运维误读「有数据但请求未成功」的中间态）。
- **`crawl/run.py` 单文件 1612 行**（P1，已被 13 §7.1/P1-19 跟踪）。承载源/批次/请求状态机、fencing、跨库写、租约、派发、cron、监控、Agent 注册全部逻辑。前瞻含义：多 worker/Leader 化时，分散且各自开事务的状态迁移难集中加锁与审计。建议按 13 §7.1 抽显式状态机模块（每个合法迁移一函数 + compare-and-set + 记 task_event）。

## 4. Agent 采集能力与协议

协议与容错底座扎实（稳定 node_uuid 重连、DB 时钟租约、attempt fencing、逐跳 DNS 防 rebinding、401/403/451 统一「暂停转人工」；`fail_when/layout_match/BFS-DFS/max_depth` 现已真正生效）。天花板集中在合规礼貌性与执行力：

- **零 robots.txt 合规 + 限流只到 source 粒度不到 host**（P1，NEW）。`CLAUDE.md` 红线明确要求遵守 robots.txt 与速率限制，但 packages/apps 全量 grep `robots` **命中 0 处**；`SourceRateLimiter` 以 source uuid 为 key，多个源命中同一 host 时各持独立桶、可叠加压垮同一站点。对要对外发布的采集产品，这是「能否合法推广」的门槛而非优化项。**建议**：抓取+缓存 robots.txt，命中 `Disallow` 走 `ACCESS_PAUSED` 通道；限流增加 per-host 令牌桶/并发闸，与 per-source 取 min。
- **契约不兼容时 Agent 无限静默重连**（P1→P2）。`conn.py:345` 只对 1008 特判，其余关闭码（含 1002 版本不兼容）一律通用退避重连，且 `conn.run` 全程无日志。未来抬 MIN 时，旧 agent 会「静默 flap、日志空白」，把一眼可定位的版本问题变成排障黑洞。**建议**：对 1002/1003 等永久拒绝码停止重连并打印「契约版本 X 不被主控 [min,max] 接受，请升级」。
- **spool 断点续传被 requeue-on-disconnect 抵消**（P2）。agent 结果先落盘 spool 再发（`conn.py:317`），但断连时主控 `requeue_agent_inflight` 把 attempt+1，重连重发的旧 attempt 结果被 fencing 判 stale 丢弃。net 效果：spool 只在「主控重启且 attempt 未推进」的窄窗真正生效；agent 每次抖动、算完只差 ACK 的 Browser 结果都白白重跑。**建议**：断连给短宽限期让 agent 重发同 attempt，或对「同 req、内容指纹一致但 attempt 落后」放行为幂等接受。
- **点选插件成熟度**（P2）。`manifest.json:8` 用 `<all_urls>` + 全页注入（商店/企业审核高风险信号）；`selector.js` 只生成单元素选择器，采集规则最核心也最难手写的 `item_locator`（列表页行选择器）和 API 源 jsonpath 都点不出，且生成的选择器不经解释器回灌校验。**建议**：支持点选归纳 item_locator（选两个同类节点归纳行选择器）与 API JSONPath；改 `activeTab` + 按需注入；回填时用同款解释器对样例页实跑形成「点选→校验→保存」闭环。
- **出网身份/网络区未进数据模型；`payipa/proxy` 只剩僵尸字节码**（P2）。`proxy/` 目录源码已删、只剩 `__pycache__`（误导后人以为能力存在）；source 模型只有 `allowed_domains`（访问哪些域），无「从哪个网络出口访问」维度。红线禁的是**动态**切换出口规避访问控制，但合规、静态、可审计的 per-source 出口绑定（内网源 vs 公网源、不同租户走不同专线）与红线不冲突。**建议**：清理僵尸 `.pyc`；把「网络区/出口」纳入 source 配置与 CapabilityManifest，派发按网络区亲和选节点。

> 引擎执行力（Browser Pool、ActionPlan、CapabilityManifest 的 per-engine 槽、结果分块续传、会话保险库、Trace/Replay）已被 13 §8 系统跟踪。补充一个**契约级排期建议**：当前「单一 slot_n + 单维 cap-filter」的假设深植于 Capabilities 契约、hub 记账、dispatch 过滤三处，落地多引擎独立槽必然是跨 contracts/hub/scheduler 的破坏性变更——应与结果分块协议一起，作为**一次 v5 契约抬升**统一解锁，避免多次破坏性变更。

## 5. 功能模块完整性（设计 vs 实现）

主干完整度高，但对照 00~12 设计文档有几处「承诺但悬空/半空」：

- **后端韧性/清洗/版型能力已实现，却没有任何配置入口（隐藏能力）**（P1）。契约与解释器完整支持 `fail_when`(软失败)、`layout_match`(版型)、爬行深度/BFS-DFS、字段级 15 个清洗算子；但建源表单（`sources.py:210-260`）定位器**硬编码 CSS-only**（xpath/jsonpath/regex 选不了），清洗链除 link 自动补 url_normalize 外无法配置，`fail_when/版型/深度/connector_type` 完全无 UI。**用户会以为平台不支持 XPath/不支持判失败/不支持深度爬行，而事实是支持只是没暴露**。这是最高性价比的一类工作——「接出已实现能力的开关」成本远低于「造新向导」，应与 13 P1-02/03/29 的表单重构一起、优先接开关。
- **用户生命周期自动化缺失：停用用户的 cron 任务继续被调度**（P1，NEW）。`03 §2.5` 承诺「停用不删 / 交接向导 / 名下有资源不可删 / 停用级联暂停并告警」四件套，代码只实现了软删（`User.status`）。`manage.py:69` 的 `set_user_status` 只改状态字段无级联；`due_schedules`（`run.py:1488`）不校验 task owner 用户状态 → **停用用户名下的周期数据源继续被抓取**（设计明确想避免的「无主任务静默运行」），也无 owner 转移端点。**建议**：停用用户同事务暂停其 owner 的周期任务并发通知；scheduler 到期建批前校验 owner 状态；加交接向导端点。
- **任务链式关联（`chain_task_id`）只是空 schema**（P1→P2，NEW）。`03` 承诺链式模板（A 输出→B 种子）降低运营认知负担，`Task.chain_task_id` 列存在（`pyp.py:190`）但全仓除定义外零引用，`on_batch_finalized`（`triggers.py`）不触发下游。看似支持实则不通，易被后续开发误判为「已具备」。**建议**：短期先明确标注为未接线预留；中期在批次收尾钩子补链式触发 + 字段映射 + 血缘串联。
- **系统级告警引擎缺失**（P1，13 P1-16 跟踪，补方向）。`notify()` 全仓仅两处调用（手动测试、批次收尾进度）；多处代码注释写了「+告警」却无落点——push 死信、磁盘低水位、整源 `ACCESS_PAUSED`、停用用户任务暂停均静默。**建议**：把告警作为独立的「事件→规则(阈值/去抖/静默窗)→渠道」编排能力设计，`monitor` 的 `SourceHealth` 已是现成数据源；先做死信与整源暂停两类最高价值告警。
- **Connector 五形态只落地 web/api**（P2，NEW）。缺 `push`（webhook 接收源，事件驱动集成）与 `feed`（RSS/Atom 增量）。**建议**：优先规划 webhook 接收源（带鉴权/去重的入站端点，复用 ingest 幂等入库），成本低且解锁事件驱动集成。
- **数据质量校验规则缺失**（P2，NEW）。现有质量能力止于 `fail_when` + `FieldMeta.confidence` + monitor 的 parse_ok/blank 率聚合，无用户可配置的非空率/值域/唯一/行数区间/schema 漂移期望，也无「质量不达标阻断入库/发布/告警」。对标 dbt test / Great Expectations，这是数据平台的差异化能力，且能复用已有证据链。
- **配置导入导出/环境迁移缺失**（P2，NEW）。只有整库 `backup/restore`，无「选择性导出源+规则+组装+推送配置为可移植包并导入他环境（凭证以引用占位）」。规则/组装已内容寻址+版本化，导出为声明式包的基础已具备。

## 6. 前端与用户体验

管理台在设计系统（CSS 变量、4 套皮肤、Toast/ask 统一反馈、无样本语义、移动端账号出口）与首启/首用向导上做得扎实。核心差距是「技术人员能用」到「目标用户能连续、可恢复地完成工作」：

- **数据组装在管理台完全无创作/编辑入口**（P1，13 P1-05 跟踪）。`/assemblies` 只有列表+状态流转+发布签名，无「新建组装」按钮、无脚本编辑器、无脚本 blob 上传端点（`AssemblyStore.put` 从无被调用）。`crawl→assemble→push` 主链中段在产品内是死胡同——用户拿到原始数据后除非直接写 Python 调 core，否则无路可走。这不是「页面只读」而是**能力入口缺失**，直接决定「组装」这条卖点能否兑现。
- **数据源建成后无法在 UI 内编辑**（P1，13 P1-02 跟踪）。`sources.py` 无 edit/update 路由，`/sources/new` 表单永不预填既有源；后端其实支持「同短码 re-POST = 更新参数+新建规则版本」，但这一行为完全不可发现。用户选择器写错导致采集空白时，只能凭记忆重敲全部字段。能力具备、UX 未接线，低成本高价值。
- **无面向浏览器的推送通道（SSE/WS），全靠轮询**（P1）。页面实时性全为 `setInterval` 轮询（ops-center 5s / monitor 10s / dashboard 15s / nodes 3s），全仓无 `EventSource`；刷新用 `renderTable` 整块 `innerHTML` 覆盖，运行态每 10s 重建整表会打断用户的横向滚动/选中/复制。主控已有 AgentHub WS 基座却无浏览器推送。**建议**：为运行态引入 SSE 承载批次进度/节点上下线/outbox；渲染改按行 key 差量更新 + `aria-live`；轮询降级为兜底。
- **配置/推送要求手写 raw JSON 与 Python 源码，凭证明文贴入 textarea 无掩码**（P1，13 P1-31 跟踪，补安全-UX 角度）。`config.html`/`push.html` 的 api_key/token 直接贴进可见 textarea，无 `type=password` 掩码，可被肩窥/截图。**建议**：按 provider/type 生成 schema 表单，凭证字段掩码显示、支持只填增量而非每次全量重贴。
- **导航对所有角色全量渲染，无 capability map**（P1，13 P1-18 跟踪）。运营/审计角色看到用户管理、密钥、发布等入口却点不动、只撞 403 空壳。`page_ctx` 已解析真实 roles，离产出 capability map 只差一步。
- **数据查看页 `autoColumns:true` + 暴露实现术语**（P1，13 P1 跟踪，补角度）。列全自动 → 日期显原始串、link 不可点、系统列（指纹/内部列）与业务列混排且无法隐藏；页面文案直露「Tabulator remote / 服务端译 SQL」；同步导出无进度、无行数上限。这是用户查看采集成果的**第一价值兑现点**，却体验最粗糙，应最先精修。**建议**：列定义由服务端下发（含类型/标签/链接化/隐藏系统列）+ 列显隐/保存视图；导出纳入运行中心异步化。
- **无 i18n 基建**（P2，NEW）。模板/`views.js`/服务端 `HTTPException detail` 三层全硬编码中文，`<html lang="zh">`，无字符串外置层。其中「服务端异常消息=前端展示文案」最危险：让 API 错误契约与 UI 语言绑死。即使 v1 只发中文，也应借 P1-17（统一错误码）之机把服务端错误改为「稳定错误码+参数、前端按 code 映射文案」——一步同时服务 i18n 与错误可定位。
- **无暗色模式**（P2，NEW）。设计系统已 token 化但 4 套皮肤全是浅色，全仓无 `prefers-color-scheme`。数据运维台是长时间盯屏工具，暗色是可访问性基线（与 13 §10.8「先别加装饰皮肤」不冲突）。补一套暗色 token 成本极低，且皮肤偏好应从 localStorage 落到用户设置以跨设备一致。
- **htmx 已 vendored 却零使用、内联 JS 遍布**（P1，13 P1-18 跟踪）。仅 `data.html` 引入 htmx 却无任何 `hx-*`；交互全走内联 `<script>`+fetch，重跑逻辑在两个模板各写一份。内联 JS 是 CSP 去掉 `unsafe-inline` 的直接阻碍。**建议**：定型交互主线，内联 JS 抽为 ES module 静态文件，公共动作抽共享模块。

## 7. 部署运维与可观测性

P0-02/03 之后，部署编排、三探针、单实例锁、preflight 门禁、冷备/升级/恢复已相当扎实。缺口在可观测性从「能探活」到「可诊断」：

- **structlog + correlation id 全程未接线**（P1，13 §12.3/P1-15 跟踪）。多处文档声称用 structlog + 全链 correlation id，但全仓无一处 `import structlog`，也无任何 `logging.dictConfig` 入口；`docker logs` 得到无结构纯文本，日志里根本没有 `batch_id/task_id/attempt_id`。SDD 承诺的「日志↔artifacts↔task_events 互跳排查」无法兑现。**建议**：在 lifespan 里配一个极小的 structlog JSON 处理链 + 统一 schema + 脱敏，加 ASGI 中间件生成/透传 `request_id`（contextvars 注入）。这是 P1-15 里成本最低、能立刻解锁 §3.6 诊断验收的一步，应先于 metrics。
- **无 `/metrics`、无 trace、无默认告警、无 support-bundle**（P1，13 P1-15/16 跟踪）。`readyz` 已逐项算出 config/三库/迁移/存储/后台环状态，`runtime.py` 的 `LoopHealth` 已持有 `consecutive_fails/last_error/last_ok_at`——这些是现成指标源，导出 Prometheus 几乎零边际成本。补 `/startupz` 区分初始化未完成；`pypctl` 加 `support-bundle`（脱敏配置+version+迁移+readyz+队列统计，明确不含密钥与采集正文）。
- **task_events/audit_log/data_* 无保留清理与分区**（P2，13 DB-017/P2-05 跟踪）。`docs/09` 宣称 audit_log+task_events「默认保留 30 天」但代码无任何删除逻辑；data_* 无时间分区。到千万行量级时查询/导出/备份/reconciliation 全部变重，事后引入分区需在线迁移大表。**建议**：先补最便宜的 30 天保留删除后台任务（与 GC 同一后台环），把文档承诺变真实现；中期在动态建表 DDL 就预留分区键。
- **compose 直暴明文 HTTP、无反向代理/TLS/真实客户端 IP**（P1，13 §3.1/§3.4.6 叙述，未编号）。运维随手加 Nginx 后，主控看到的都是代理 IP，登录限流/审计/逐跳域校验拿到的 IP 全错；长连 WS 无代理侧空闲超时约束。**建议**：发布 compose 加反向代理服务（Caddy/Traefik）负责 TLS/WS Upgrade/请求体上限，主控启用 ProxyHeaders 正确解析真实 IP。
- **运行时最小权限缺失**（P1，13 §3.2.3/§3.4.4 叙述，未编号）。initdb 以 postgres 超级用户建库、compose 各服务都用 `PG_USER=postgres` 连全部三库（红线「跨库不 join」只靠代码自觉、无 DB 账号权限兜底）；容器无 `mem_limit/cpus/pids_limit/ulimits`、无 read-only 根、无 json-file 日志 `max-size/max-file`（长期运行会以另一种方式写满盘）。这些纯配置、风险低、收益直接。

## 8. 测试与质量工程

62 文件约 7900 行，核心并发/状态机不变量有针对性回归，CI 已接真三库。结构性天花板在「代码翻倍后会变慢、变脆、看不见回归」：

- **测试隔离靠固定标识符 + 手工 DELETE + 全局表耦合**（P2，NEW）。几乎所有 `_pg` 用例用进程内硬编码短标识（如 `_UUID="m2disp"`）+ finally 里手写级联 DELETE；conftest 的 `_reset_caches` 只清 lru_cache 不重置 DB。`test_sandbox_pg.py:61` 的 teardown 注释已记录跨用例污染事故。后果：固定标识符 + 共享库使 `pytest-xdist` 并行不可行、用例崩溃留孤儿行、新增关联表极易漏删。**建议**：择一落地统一隔离（SAVEPOINT 回滚 / 每用例唯一 uuid 前缀 + autouse 前缀清理 fixture），把清理收敛到共享 fixture，然后开并行。
- **金字塔倒挂 + 无测试分层**（P1，13 §13.2 跟踪一半）。40/61 依赖活 PG，纯单元层稀薄；`pyproject.toml` 无 markers 注册，CI 单条 `pytest` 一次跑全部。开发内环没有秒级单元层可依赖，任一环境抖动整轮变红且无法定位是哪层坏。**建议**：注册 markers（unit/pg/sandbox/browser/e2e）并给现有用例打标，CI 拆并行 job（unit 为 PR 必过），有意识补脱库单元层（interpret/清洗算子/url_policy/response_policy/退避游标）。
- **安全关键的沙箱/浏览器测试静默 skip，CI 无「是否真跑」门禁**（P1，13 P0-19 跟踪 PG 维度）。沙箱 egress 隔离是全系统最强安全边界，无 Linux 容器即 `pytest.skip` 且计入「绿」——一次破坏隔离的回归会带着全绿 CI 直接发布。**建议**：CI 用「必须运行」语义（Docker 就绪失败即 fail 而非 skip）+ 断言该 job 用例数 > 0；补隔离边界的**否定测试**（脚本访问白名单外域/路径应被拒），而不仅正向 happy-path。
- **契约兼容 skew / 迁移升级测试缺失**（P1→P2，NEW 增量）。`test_contracts.py` 只断言纯函数布尔，无「用真实旧版帧走 WS 握手被干净拒绝」、无历史版本 golden fixture（防「旧帧被新模型静默误解析」）。CI 迁移只做 `upgrade heads`，缺「上一发布版→head + 灌旧格式数据」的升级演练（`reconcile` 类迁移在真实数据上最易出错却零覆盖）。
- **无 mypy/pyright 与覆盖率门禁**（P1，13 §7.5.3/§13.9 跟踪，仅建议）。系统大量在 int state / 负数错误码 / UUID / 时钟做手工约定，ruff 抓不到类型层契约漂移。建议先在 contracts+状态机+service 层引入 pyright（增量、非阻塞起步），coverage 对 crawl.run/outbox/security/迁移设分模块阈值。

## 9. 安全与数据生命周期

安全底座真实且不少环节扎实（域白名单+逐跳 DNS 防 rebinding、KEK/Fernet 信封、token 只存 hash、argon2、CSRF 双提交、生产 preflight 硬门禁、安全响应头）。13 号文 P0-17/P0-18 确已落地。纵深与生命周期的结构性薄弱：

- **RBAC 是扁平全局权限，缺对象级/资源级授权**（P1→P2，NEW 接口缝）。`has_permission(perms, code)` 是扁平集合判定、无资源维度，四角色是固定矩阵。「用户 A 只能看数据源 X」无法表达（「只读分析员」其实可通过 seed 一个仅含 `*.read` 的角色实现）。权限码只会越加越多，将来加对象维度必须改 `has_permission` 签名 + 所有 `require_perm` 调用点 + 存储 + 数据查询过滤。**建议**：现在就把判定接口留出对象维度 `has_permission(perms, code, *, resource=None)`，v1 只实现 `resource=None`，把缝留好。
- **审计覆盖窄 + best-effort + 无防篡改**（P1）。`record_audit` 全仓仅 6 处调用，而模块 docstring 宣称覆盖「SQL 查询、规则发布、强制入库、权限变更」——实际 RBAC 授权变更（grant/revoke/make_superuser）、force_insert、发布、登录成功/失败、SQL 查询全部**未落审计**；全走 `record_audit_best_effort`（写失败仅告警，与「权限/发布/凭证/删除不应 best-effort」相悖）；`AuditLog` 无 request_id/ip/ua/result，无 append-only/哈希链（超级用户可静默改删）。**建议**：定义须审计动作清单，高危动作改「与业务同事务的强审计」；补 ip/ua/result；规划 append-only（DB 触发器禁 UPDATE/DELETE）或哈希链 + 审计查询 UI。
- **KEK 单轮 SHA256 派生、信封无 key version**（P1，见 §2 D10）。`secrets.py:23` 无 salt/正规 KDF，密文无 `key_version` → 轮换必须试解每行、无法灰度、实质锁死；泄漏后除逐条重录无轮换手段，丢失则所有密文永久不可解。**建议**：改 HKDF/scrypt/argon2 派生或强制 32B 随机 KEK + 长度校验；信封加 `key_id/version` 前缀支持多 KEK 共存 + `pypctl kek-rotate` 批量重包裹（幂等可续跑）；restore 按 version 匹配而非要求 KEK 恒等。
- **采集数据无生命周期治理**（P1，NEW；与 §2 D1 同源）。data_*/asm_* 无 `expires_at`/`deleted_at`/保留期，无「按 source 级联删除（元数据+动态表+raw+artifacts）」，无数据主体删除。面对删除请求/导出合规/按源清退只能手工逐库 SQL。**建议**：先把 GC 接后台环（见 D1），再规划数据生命周期框架（可配保留期 + 级联删除作业 + 软/硬删除分离 + 删除审计 + dry-run）。
- **会话 JWT 无 jti/issuer/audience、无主动撤销**（P1，NEW）。`create_session` 只签 `{sub,u,exp}`，会话默认 7 天。停用用户可即时失效（每请求回查 status），但令牌泄露/设备丢失/改密/降权后无法即时收回、无「登出所有设备」。**建议**：加 `iss/aud/jti + token_version`（改密/降权时 bump 使旧会话失效），jti 落审计便于吊销。
- **供应链无 SBOM/漏洞扫描/密钥扫描/镜像扫描，基础镜像未按 digest 固定**（P0，NEW；13 §11.11/§13.11 叙述未编号）。CI 无 pip-audit/trivy/gitleaks/签名；`Dockerfile.server` 用浮动 tag `python:3.14-slim`。对外分发前无漏洞可见性 + 基础镜像随 upstream 漂移。**建议**：发布前 CI 加 SBOM(syft)+CVE(pip-audit/osv)+镜像扫描(trivy)+secret 扫描(gitleaks)，基础镜像按 sha256 digest 固定 + cosign 签名，设为发布门禁。
- **源站登录凭证无金库**（P2，13 P1-10/13/23 跟踪）。`Credential` 表存在却是孤立死表，无「登录型数据源凭证」的存储/注入路径。建议接线为统一 Secret Vault（KEK 信封+scope+轮换+审计）或明确删死表；规划会话保险库（主控只向 Agent 下发短期 scoped 会话租约，长期凭证不出主控）。

## 10. 平台化：四个「向外看」的整维缺口

九维评审系统性偏「向内看」（把 payipa 当作要跑对的软件）。以下四维决定它能否成为「可集成、可追溯、有生态、可运营的平台产品」，越晚补牵动面越大：

- **M1 · 对外集成与公共 API 演进策略（P1，NEW）**。唯一机器面是只读 Dataset API（`X-API-Key`+keyset），且**全部路由用无版本前缀 `/api/*`**（`datasets.py`/`api.py`/`ai.py`/`config_mgmt.py`/`studio.py`/`manage.py`）——一旦有外部集成方接入，任何 REST 破坏性变更都会静默打挂对方（与团队在 Agent 契约侧的郑重版本管理形成反差）。还缺出站事件订阅（下游只能轮询）与声明式管理 API / client SDK。**建议（发布前落最便宜的结构缝）**：对外契约引入 `/api/v1` 前缀，内部 SSR/htmx 路由用 `/ui` 或 `/internal` 段隔离，openapi 分组，文档明确「哪些是对外稳定契约、弃用窗口多长」。中期做机器管理 API（GitOps 声明式创建源/规则）+ 出站事件订阅（复用 outbox 基础设施推送平台事件、带签名重试）+ 薄 Python client SDK。（13 P2-08 跟踪的是**入站** Connector/Plugin SDK，与此**出站集成/消费面**不同方向。）
- **M2 · 数据血缘 / 端到端可追溯（P2，NEW）**。building block 散落却未串成链：task 带 `rule_version/rule_hash` 派发快照、采集行带 `batch_id`，但**组装环节把 `batch_id` 当系统列剥离**（`studio/gateway.py:19`），Dataset API 返回的行无任何来源标识。下游拿到一行数据无法回答「来自哪次采集、哪个规则版本」，出脏数据无法定位波及范围。这与「correlation-id 打通日志」（运维排障维度）不同——这是**数据记录本身**的血缘维度，是与 dbt/Airbyte 对标的合规与可信底座。**建议**：定义贯穿主链的最小血缘模型（batch→source/rule_hash/task 可查询映射 + 组装产物保留来源引用或独立 lineage 边表），近期先做「行级来源徽章」，中期做可导出血缘视图，为合规删除/撤回与质量根因分析提供落点。
- **M3 · 生态 / 内容分发（P2，NEW）**。产品把降低非技术用户门槛作为卖点，但建源只内置一条硬编码示例（`books.toscrape.com`），无源配方模板库/一键添加常见站点/规则包分享——用户仍要从零手写最难的 `item_locator`。而规则/组装已内容寻址+版本化，是做可分享内容包的理想基质（几乎白得）。**建议**：近期先做只读「源配方模板库」（内置示例扩成可浏览、可一键实例化的模板集），中期把规则/组装导出为声明式可分享包（带签名+来源标注，导入需管理员复核发布，复用现有签名门），天然对接 M1 的声明式管理 API 与 AI 辅助建源。
- **M4 · 商业化运行能力（P2，NEW）**。P0-22 只解决了法律/支持文档（proprietary LICENSE、SECURITY、CHANGELOG），运行期能力全空：无使用计量（跑了多少源/多少数据量/哪些用户活跃）、无授权 entitlement 执行、**更缺对自托管客户至关重要的遥测隐私姿态**（是否回传、回传什么、能否关闭）。自托管客户对静默 phone-home 高度警惕，缺一个书面 opt-in/out 承诺会直接卡住企业安全评估。**建议（先定姿态与轻计量）**：明确声明默认不回传（或仅本地可导出的匿名摘要、管理员显式 opt-in 才外发）并写进 SECURITY/隐私说明（信任前提、几乎零成本）；同步做本地使用计量面板（活跃源数/采集量/AI token 成本已有溯源可复用），既服务容量运营也是未来分层/计费的度量地基。

## 11. AI 能力：地基已打好、楼还没盖

AI 层地基质量高、边界干净（ModelRegistry 凭证信封加密 + LlmGateway 单一出网入口+成本审计落库 + 自研 provider 抽象 + 真集成测试）。但**面向产品的 AI 能力几乎全部未接线**，是当前最「言过其实」的维度——管道通了，差异化价值尚未兑现：

- **`ctx.ai()` 运行期完全未接线 + 跨多篇文档漂移**（P1，NEW）。沙箱交给用户脚本的 `GatewayContext` 只有 `read_table`，无任何 ai 方法；`gateway.complete` 唯一真实调用方是 `/api/llm/complete` 与测试。而 SDD/04A/08 都把 `ctx.ai()` 当已定能力反复引用（04A 还承诺「结构化输出校验」）。**建议**：先把文档措辞统一改为「未接线(planned)」消除误导（P0 级文档动作）；实现路径是在容器 egress 白名单加一个「LLM 代理端点」（类比 Query Gateway 的 job_token 模式），沙箱 `ctx.ai(prompt, schema=...)` → HTTP 到主控代理 → `gateway.complete`（凭证不出主控），且必须同时落地结构化输出校验。
- **承诺的核心差异化「AI 帮写规则/组装、一键生成」在任何界面都不存在**（P1，NEW）。唯一 AI 界面是 config 页的模型登记；建源/规则/组装页无任何 AI 入口；contracts 里也没有 `ai_model/system_prompt` 字段（决策记录已拍板的「配置新增 AI 模型字段」未落地）。地基都在却没接成用户闭环。**建议（最小垂直切片）**：规则页「AI 辅助生成规则草稿」——贴 URL/DOM → 带库白名单+固定方法的系统提示词生成声明式规则草稿 → 进现有 test 通道试跑 → 人审签名发布。完全复用 test-channel + 签名门（红线7），风险可控、价值最高；把 test 试跑的字段命中率记进审计，从第一天积累生成质量数据。
- **LLM Gateway 无成本上限/配额/限流/缓存/失败降级**（P1→P2，NEW）。`gateway.complete` 只「解析→调 provider→记审计→原样抛」，审计是事后记账不是事前限额。当前只有管理员能触发风险有限，但一旦 `ctx.ai()`/AI 辅助建源开放给非管理员，一个死循环脚本就是一张真实账单。**建议**：加预算/配额中间件（全局+per-owner+per-task 日/月 token 与美元上限，超限 fail-closed 并审计）+ 令牌桶限速 + 按 (model,system,prompt hash) 短期缓存 + 失败退避 + 可配降级模型链。必须先于「AI 面向用户开放」落地。
- **provider 仅 Anthropic + echo**（P1，NEW）。自托管、处理用户业务数据的产品，很多客户（隐私/合规敏感或内网）不接受把清洗中的数据发往境外云 API，或根本无出海通道。单一 provider 直接把这批用户挡在门外。**建议**：优先补一个 OpenAI 兼容 provider（一个实现覆盖 vLLM/Ollama/本地网关/多数聚合网关，性价比最高），管理员可指向自有 endpoint；进一步在数据源级加「AI 数据出境策略」开关。
- **系统提示词治理不完整**（P1→P2，NEW 增量）。`SystemPrompt` 表只有 content+version 整数，`set_system_prompt` 直接 UPDATE 覆盖旧内容（无历史、无 diff、无回滚），且全仓无默认提示词种子（与 08「项目默认提供」相悖）。系统提示词是 AI 生成质量的总闸，无种子则管理员开箱得空白框、AI 生成翻车，改坏又无法回退。**建议**：改「不可变版本历史 + 指针」模型；开箱种子一份默认提示词，内容从「固定方法 SDK + 库白名单」文档**同源生成**。
- **务实的中期 AI 方向**（P2，NEW）：(a) **失败任务 AI 诊断摘要**——把一批 requests 负码 + field_meta 降级证据喂 AI 产出「根因摘要+建议动作」挂在错误/监控页（只读、无副作用、按需触发天然控成本，是最早能交付的可感知 AI 价值）；(b) **自然语言查数**——因 Query Gateway 已把取数收窄成「类型化 filter DSL + keyset」，让 AI 只把 NL 翻成 `ColumnFilter[]`（而非生成 SQL）就天然复用这条安全边界，是别家想做要额外造安全层、payipa 几乎白得的差异化，务必**锁定架构决策：任何 AI 取数一律编译到 Query Gateway DSL，不开 NL→SQL 口子**；(c) **规则自愈**——需先补最上游的「字段级命中率/空值率漂移检测信号」（不需要 AI 的独立高价值功能），再在其上挂 AI 修复建议走 13 §8.7 的 fixture+人审+签名轨道。
- 工程小项（P2）：硬编码价目表会过期、未知模型成本记为 None（成本溯源可信度衰减）；缺 AI 生成产物的质量评估机制（golden fixture 准确率 + AI/人写通过率对比）。
