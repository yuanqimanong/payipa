## 1. 需求对齐

### 1.1 需求方口述（第 1 轮，2026-07-05）

1. **出口就两种**：提供 API + 发请求给下游。推送有专门页面：**提前用 Python 写好推送逻辑，发布成「推送组件」**。例：写一个「推送 Ghost 博客」组件——组装数据备好要推送的字段 → 链路下一环挂上该组件 → 组装产物查看页**每条详情带推送按钮**（点击即按组件逻辑推到对应接口）。另一形态：**数据任务跑完批次+组装完毕，自动触发推送**。API 模式也可供 AI 阅读。
2. **定时推送**：推送可单独配定时——如**定时推送每台机器情况到 lark 群、邮件等**（推什么看组件代码逻辑，不限于业务数据）。
3. **按批次推送**；重复靠**下游去重**，平台随数据提供**数据指纹 id** 支撑该逻辑。
4. ✅ 失败重试复用 07（次数+指数退避）、连续失败死信+告警。
5. ✅ Dataset API = Query Gateway 对外版（字段过滤+keyset 分页）；API key 鉴权（可吊销/配额/按 key 限流）；AI 靠 OpenAPI 机制，MCP 归 08。
6. **通知机器人（用户级）**：每个用户可配置**属于自己的 lark 机器人**，选择不同机器人通知不同任务的进度/状态；机器人可配置到任务中。
7. ✅ 推送记录与告警通道都要可配置。
8. ✅ 推送 = 07 任务体系的一种任务类型。

### 1.2 整理（助手，同轮）

- **推送组件 = 第三类脚本**，完全复用 02/04 脚本基建：固定方法名、管理员签名、代码执行器执行、版本状态机（draft→testing→active）+ 内容寻址。**三种触发**：①手动（详情页按钮，单条）；②链路自动（批次组装完毕，按批增量——水位机制复用）；③定时（cron，内容由代码定：业务数据或系统状态通知，机器状态数据源自 contracts monitor.py）。
- **幂等责任边界**：平台不记「下游已收过什么」——随数据附指纹 id，去重责任在下游。简单、无状态、可横向重试。
- **通知渠道与推送组件分层**：lark 机器人/邮件是**内置轻量通知渠道**（用户自配 webhook/收件人、绑定任务，无需写代码）；推送组件是**代码类出口**（技术编写发布）。两者并存互不替代。
- **凭证两类**（默认记法，待复核）：①通知机器人凭证 = **用户级自配自管**（口述明确）；②推送组件的下游目标凭证（如 Ghost API token）= **组件级配置项，DB 加密存储**，技术配置、管理员可管理——同 02 签名密钥「管理员统一、用户无感」的思路。
- **沙箱出站问题（挂 04A）**：推送组件要向任意下游接口发请求，与组装沙箱「egress 仅放行 gateway」冲突——推送组件固定在主控本地执行器跑，或按组件声明目标域白名单——归 [04A](04A-沙箱执行服务.md) 一并定。

## 2. 技术调研

- 本轮无需新调研：lark/邮件 webhook 为常规集成；其余全部复用既有机制（Query Gateway、07 任务体系、02/04 脚本基建、keyset 流式）。API key 签发/配额的实现细节（PyJWT 或随机 token+hash 存储）留实现期定。

## 3. 可行性验证

- ✅ 已实现（含 PG 集成测试）：「编写→签名→发布→三种触发」全链路——组件登记/发布/状态（`routers/api.py` + `PushComponentStore` 内容寻址 + HMAC 签名门）、手动入队（`enqueue_push`）、链路自动触发（`triggers.on_batch_finalized`）、cron（`scheduler` + cronsim）、outbox 排空（`consumer_loop`）；Dataset API keyset 深翻页（`deliver/dataset.read_dataset` 回 `next_cursor`）。**仅剩「按 key 限流」冒烟为待办**。

## 4. 定案（2026-07-05，详见 [决策记录.md](决策记录.md)）

1. **出口两种**：对外 Dataset API + HTTP 推送下游；不做 DB 直写/MQ/SFTP 等固定目标类型——**组件模型天然可扩展覆盖**。
2. **推送组件模型**：Python 写推送逻辑 → 发布成组件（复用脚本基建与版本机制）→ 挂到链路/按钮/定时。
3. **三种触发**：手动单条（详情页按钮）/ 链路自动（批次组装完毕推增量）/ 定时（内容由代码定，含系统状态通知）——**三触发统一走 outbox**，手动按钮点击即入队、返回「已入队」；cron/系统状态类推送的数据供给由 **Consumer 把 monitor 快照物化进 `payload_ref`**。
4. **批次推送 + 指纹下游去重**；**复用 07 的重试/退避/死信语义**（次数+指数退避、连续失败死信+告警）；执行走 **push_outbox + 主控 Consumer**（绝非 agent Redis 队列）。**主控推送执行器 = 隔离子进程**，仅注入（payload 数据、该组件解密后的目标凭证、目标域白名单），无 DB/KEK 访问。
5. **Dataset API = Query Gateway 对外版** + API key（吊销/配额/限流）；对外响应 = **JSON 行 + keyset `next_cursor`**（OpenAPI 记录，区别于内部 Arrow IPC）；AI 消费靠 OpenAPI；MCP 归 08。
6. **用户级通知机器人**：lark 机器人（及邮件等）用户自配，绑定任务通知进度/状态。
7. 推送记录（范围/条数/成败/下游响应/耗时）入审计，告警通道可配置。
8. **Outbox 可靠投递（汲取点②，2026-07-05 纳入）**：推送经 **push_outbox 表 + 独立消费循环**解耦，**非跨库 2PC**——`data_*`/`asm_*` 业务产物落库后，**在 pyp 侧同一事务内置产物状态 + INSERT push_outbox**（outbox 属 pyp 控制面、非 business 产物写），即「**先写数据 → 再置状态 + outbox**」；靠 `idempotency_key` 幂等 + **轻量对账兜住「数据已落、状态/outbox 未落」的残窗**，配合死信抗主控崩溃/下游抖动。**contracts 加 `OutboxState` 枚举**（`pending`→`inflight`→`sent`|`dead`）+ **死信阈值默认**（连续失败 N 次转 `dead` + 告警）。**outbox 表字段**含 `next_retry_at`(退避)/`lease_until`(消费租约防重复消费)/`last_error`/`attempts`/`idempotency_key`/`owner_id`（详见 [SDD §4.1](软件需求与详细设计说明书.md)）。
