## 1. 需求对齐

### 1.1 需求方口述（第 1 轮，2026-07-04）—— 从前端配置页视角

1. **配置流程（一个数据源的诞生）**：
   - **数据新增页面**：数据分组、数据描述（发布后供用户任务界面选择该能力）、队列优先级 / 分发集群、重试次数、超时时间、自动调频/限流等——正好是 07 已定任务模型的配置入口。
   - 数据来源两类：**网址监控 URL 列表** 或 **授权 API 访问接口**。
   - **规则配置 = 解析**，两大分支：
     - **人工配置**：a) **自己填**——新增字段，填 xpath / css / jsonpath / regex 定位；页面配「获取源码（调用 agent）或手填源码」做本地测试，逐字段看提取效果；b) **浏览器插件点选**——插件定位并自动回填（清洗仍人工写），接 10 模块。
     - **AI 帮配**：提前教给 AI 平台的固定方法，AI 直接编写 Python 脚本实现多字段配置；人工也可直接写脚本走同一通道——细节归 08-AI 能力。
   - **字段级清洗**：需要清洗的字段下有「清洗逻辑」按钮——**工具箱**组件供用户组合逻辑，也可添加 Python 脚本（**脚本有固定方法名约定**）。
   - **版型**：一套配置好的规则 = 一个**版型**；版型识别 = **URL 正则匹配 + 源码特殊值匹配**（同一 URL 形态对应多版型时，靠正文正则区分）。
   - **新链接**：字段类型三选一——**存储 / 新链 / 存储+新链**；新链字段也可挂清洗组件（URL 归一化）。
   - 以上是 HTTP 采集；**浏览器自动化采集等做到时再详述**。
2. **raw 留存**：管理员配置 S3 后，数据配置页出现「**是否开启 raw 存档**」（用于重解析与排查）；归档到 S3 或本地都经**高压缩比压缩**；raw 仅含数据链路上的**网页/JSON**，不含多媒体；**多媒体单独存 `桶/数据配置UUID/files/文件唯一ID`**；配置字段带「是否存储」选项，存储字段落对应 pgsql 数据表，**按数据分表**（分表规则最后定）。
3. **规则形态 = 纯声明式 JSON + 脚本双轨**：声明式本质是 JSON 结构，由**内置固定方法**动态解析执行；Python 脚本与该固定方法同路——都经**代码执行器**执行。**有沙箱服务则 agent 把执行任务发给沙箱、取回结果；未部署沙箱则 agent 本地执行**。脚本**签名要做，管理员统一配置**（用户无感）。
4. **执行位置 = agent（或沙箱）做解析+清洗**；raw 存本地/S3；重解析按路径拉取源数据重跑；本地要**提前检测空间**（接 01 磁盘水位）；**raw 默认保存 7 天**。提问：如何估算数据大小 → §2.4。
5. **schema**：每个数据源的字段由用户规则配置定义。提问：存 pgsql 字段扩展有无阻碍、想办法 → §2.1。多站点/多版型汇入同一 schema 靠 URL 正则 + 正文固定值正则（同版型识别机制）。
6. **去重两层**：任务 URL 去重 = **URL 指纹（url + 排序请求体）**，提问：随机参数怎么办、ajax 与自动化库 URL → §2.2；数据去重 = 用户配置**数据指纹**（业务固定组合字段，排序后算 md5）+ **唯一索引**。征询：布隆过滤器只能查不能删，感觉用不上，你怎么看 → §2.3。
7. **失败处理**：数据处理失败在 pgsql 记录 **state 标错误码（错误码固定、负数）**（类型勘误见 §1.2-2）；任务失败重回队列，达最大失败次数标记 state 并记录原因；前端有**错误数据查看页**，可点**重采 / 重解析 / 重入库**；**测试默认不入库**，勾选**强制入库**才入库（少量补数/修数用，可作运营用户的独立功能）。**角色雏形：管理员**（平台级：功能组件权限、开通账号、公共 api、参数）/ **技术人员**（数据规则配置）/ **运营用户**（补数修数）——已喂给 [06 鉴权模型](06-界面.md)。
8. **版本化**：每次规则有版本号——方便查 log、按版本号**还原配置**、按版本号**测试**。
9. 软失败判定表达形式：需求方未看懂原问题——§1.2-1 用例子重新问。

## 2. 技术调研

> 核验 2026-07-04（PostgreSQL 官方文档、w3lib 文档、HTTP Archive、zstd/Redis 官方，一手来源为主）。

### 2.1 PG 用户自定义字段：无硬阻碍，推荐「固定系统列 + JSONB + 生成列提升」混合

- **事实一（DDL 路线可行）**：PG 11 起 `ALTER TABLE ADD COLUMN ... DEFAULT 常量` 是**元数据级操作、不重写表**（默认值存目录，读旧行按需返回）——大表加列瞬间完成（postgresql.org/docs、EDB 博客）。痛点不在加列，在改类型/删列的迁移管理。
- **事实二（JSONB 路线）**：JSONB 免 DDL，GIN 索引可查任意键；但 GIN 写放大与体积明显（社区实测单 GIN 13–18MB vs 4 个针对性 B-tree 共 3.5MB）；PG 12+ **STORED 生成列**可把 JSONB 热键提升为强类型列建 B-tree，等值查询性能与表达式索引相同（crunchydata.com、richyen.com、oneuptime）。
- **建议方案**（结合已定「按数据分表」）：每数据源一张表 =
  1. **固定系统列**：id、批次/任务关联键、**数据指纹（唯一索引）**、created_at、**state smallint**（负数=错误码）；
  2. **用户字段整体进一个 JSONB 列**——规则加减字段零 DDL；
  3. 规则配置里字段可勾「**需索引/强类型**」→ 生成 **STORED 生成列 + B-tree**（少量 DDL，均无表重写）；任意键查询需求再补 GIN。
- 入库幂等：`INSERT ... ON CONFLICT (数据指纹) DO NOTHING/UPDATE`。
- 分表命名建议 `data_{数据配置UUID短码}`；单表量大再上 PG 原生分区（按时间/批次）——挂遗留。

### 2.2 URL 指纹与随机参数

- **业界基线**（Scrapy 模式；w3lib 文档已核验）：指纹 = hash(HTTP 方法 + 规范化 URL + 请求体)。规范化用 `canonicalize_url`：**查询参数按键再按值排序**、百分号编码统一大写、去 fragment、空值参数处理——需求方说的「url+排序请求体」与此一致，补上「**查询参数也要排序**」。
- **随机参数（时间戳/cache-buster/随机 token）没有全自动解法**，业界答案是**参数清理配置**：w3lib `url_query_cleaner` 原生双模式——**白名单**（只保留指定参数）/**黑名单**（移除指定参数）。建议：内置默认黑名单（`utm_*`、`fbclid`、`gclid`、`_`、`t`、`timestamp` 等跟踪/随机参数）+ **数据源级可增删**；拿不准的源直接用白名单（只留业务参数）最稳。
- **AJAX**：指纹已含方法+体；**JSON 体先按键排序再序列化**才能 hash（否则同义 JSON 不同指纹）；表单体按键排序同 URL 处理。
- **自动化（浏览器）任务**：页面 URL 相同而交互不同 → 指纹需加「交互脚本标识」维度——留自动化采集专场。

### 2.3 布隆过滤器研判（需求方征询意见）

**结论：认同 v1 不用，但理由摆正**——不可删只是其一（标准布隆确实不可删；可删的变体是**布谷鸟过滤器**，RedisBloom 两者都提供，redis.io）。真正的否决理由：

1. 权威去重已由 **PG 唯一索引**（数据）与 **Redis 精确集合 / PG 查询**（URL）承担，概率结构只是省内存的前置优化，不是必需层；
2. 布隆有**假阳性**：「可能见过」若直接跳过会漏抓从未见过的 URL；要不漏就得回查精确存储——等于没省；
3. 本项目规模（Redis 已在栈内）精确结构足够。URL 前沿到几十亿级再评估布谷鸟过滤器。

### 2.4 raw 容量估算与压缩（回答「如何估算数据大小」）

- **压缩选型**：Python 3.14 **stdlib 自带 zstd（PEP 784）**，零新增依赖即满足「高压缩比」。参考值：silesia 语料 level 3 ≈ 3.17×（文本/HTML 通常更高）；官方与 AWS Athena 建议 **level 6–9** 为压缩比/CPU 平衡点；19 是极限档（高内存高 CPU、收益边际）——建议默认 **level 9~12**，POC 实测定档（facebook/zstd、docs.aws.amazon.com）。
- **静态估算（做初值）**：HTTP Archive 2025——中位页面 **HTML 文档约 22–30 KB**（传输大小，已含 gzip/br；zstd 归档后同量级）。粗算规则 **~30 KB/页**：10 万页/日 ≈ 3 GB/日 → 7 天窗口 ≈ **21 GB**；100 万页/日 ≈ 30 GB/日 → 7 天 ≈ **210 GB**。JSON API 响应通常远小于网页。
- **真正的答案是滚动实测**：每数据源持续统计「压缩后平均大小」（前 N 页起算），存储页展示——预计日增 = 平均压缩大小 × 日请求量；预计占用 = 日增 × 保留天数；接 01 已定的**磁盘水位告警 + per-source 容量上限**，超限提前预警而不是事后爆盘。

## 4. 定案（2026-07-04，详见 [决策记录.md](决策记录.md)）

1. **规则/版型模型**：数据源配置（分组/描述/优先级/分发集群/重试/超时/调频限流）；来源 = URL 列表或授权 API；规则配置双分支（人工手填 xpath/css/jsonpath/regex 或插件点选；AI 帮配归 08）；字段级清洗 = 工具箱组合 + Python 脚本（固定方法名）；**版型识别 = URL 正则 + 正文特殊值正则**；字段类型 = 存储/新链/存储+新链（新链可挂 URL 归一化）。
2. **执行位置**：解析+清洗在 agent（或沙箱——部署了就发沙箱，否则本地）；声明式 JSON 由内置解释器执行，脚本经**代码执行器**（本地/沙箱同一接口抽象）；**脚本签名管理员统一配置**；沙箱通信按批不按条，协议归 04。
3. **raw 存档**：数据源级开关；zstd（stdlib）压缩归档（默认档 POC 定，倾向 9~12）；**默认保留 7 天**按源可配；raw 仅网页/JSON，路径 `桶/数据配置UUID/raw/{批次}/{URL指纹}.zst`；**多媒体单独存 `桶/数据配置UUID/files/文件唯一ID`**；容量 = 静态初值（~30KB/页）+ 滚动实测 + 01 水位告警。
4. **数据存储 = 按数据分表的混合 schema（表落 `data_center` 库，[09 §1.3-3](09-部署运维.md)）**：固定系统列（id/批次关联/**数据指纹唯一索引**/**created_at + updated_at（timestamptz，UTC 存、东八显示——03 第 2 轮补充定案）**/**state smallint 负数错误码**）+ 用户字段 JSONB + 勾选「需索引」→ STORED 生成列 + B-tree；`ON CONFLICT` 幂等入库（更新时刷新 updated_at）；错误码固定枚举进 contracts；业务时间字段**双存**（原文 str + dateparser 解析 timestamptz 可空，见 [03 §2.6](03-数据查询.md)）。
5. **去重两层**：URL 指纹 = hash(方法+规范化URL+排序请求体)（查询参数排序、JSON 体键排序、参数清理黑/白名单数据源级可配）；数据指纹 = 业务字段组合排序 md5 + 唯一索引（**唯一性=表内/源内**，因按源分表、无需组合键；重复采集 upsert 去重是设计目标）；**不用布隆过滤器**。
6. **失败与修复**：state 负数错误码；重回队列至最大失败次数；错误数据查看页（重采/重解析/重入库）；**测试默认不入库，强制入库为运营功能**；软失败特征 = 包含字符串 + 正则，数据源级为主、版型级可覆盖；**角色雏形：管理员/技术/运营**（喂 06）。
7. **版本化复用 01 机制**（状态机 + 内容寻址 + agent 缓存）；版本可查 log、还原配置、按版本测试；「获取源码」测试走 test 通道。
8. **API 型数据源认证（2026-07-05）**：需要 key/token 的 API 源——**key 由管理员配置**（加密存储，公共配置或数据源级），数据模块中**用脚本封装一层**处理认证（header/token/签名）与翻页；复用固定方法 SDK + 代码执行器。普通无认证 API 直接配 URL 即可。
9. **字段级 FieldMeta（汲取点①，2026-07-05 纳入）**：清洗产出每字段带 `raw_value / normalized_value / confidence / locator / warnings`；**字段级降级**——单字段低置信/解析失败不丢整条记录（标记后入库）。直接支撑 monitor 的「解析成功·失败·空白率」统计（借鉴 clearpage）。
10. **源无关 Connector 契约（汲取点④，2026-07-05 纳入）**：数据源抽象为统一 Connector 契约，五形态平权——网页 / API / **Feed(RSS/Atom) / 推入(webhook 接收) / 文件·DB**；**v1 落地网页 + API，其余契约预留形态位**，不锁死网页/API。
11. **数据表加多租户列（汲取点⑥，2026-07-05 纳入）**：`data_*` 表系统列增 `owner_id`（+预留 `tenant_id`），为将来行级权限(RLS)/计量/审计铺垫，零成本。
